# 0002：数据库说明书矛盾登记

- 日期：2026-09-13
- 状态：open
- 关联章节：`01-后端说明书.md` 第 6.1、6.5、6.9、6.10、6.11、9.4 节

## 记录目的

不修改 `docs/specs/01-后端说明书.md` 原件，只记录实现过程中发现的内部表述矛盾，避免迁移和代码各自猜测。

## 矛盾一：初始化 DDL 的执行范围

第 6.5 节一处写“以下 DDL 按外键依赖排序，可整段原样执行”，随后又明确 `0001_init.sql` 必须先拼接第 6.2 节的扩展/枚举块，再拼接第 6.5 节的表结构块；第 9.4 节又简称为执行第 6.5 节 DDL。

**当前实现决定**：仓库中的 `infra/db/migrations/0001_init.sql` 明确包含第 6.2 与第 6.5 两个 SQL 块，不能单独执行第 6.5 块。

## 矛盾二：软删除原则与 `ON DELETE CASCADE`

第 6.1 节称所有删除均为软删除，只有附件清理允许物理删除；但多处外键使用 `ON DELETE CASCADE`，物理删除上游记录时会级联删除关联数据。

**当前实现决定**：保留说明书 DDL 原样，不在迁移中私自改 FK 行为；业务层不提供这些实体的物理删除接口。若未来需要改变 FK 策略，必须新增 decision 和独立迁移，不能在业务代码中绕过。

## 矛盾三：搜索索引范围与索引 DDL

第 6.9 节描述搜索覆盖 `messages` 与 `task_comments`，且消息范围为未删除的 `text` / `task_card`；第 6.5 节的 `messages_body_trgm` 条件只限制 `deleted_at IS NULL` 与 `body IS NOT NULL`，没有限制 `kind`，也没有看到任务评论正文的对应 trigram 索引。

**当前实现决定**：`0001_init.sql` 保留原始索引，不替说明书补充推测性索引；搜索模块实现前先补充明确的 decision，再生成新迁移。

## 矛盾四：索引数量与容量估算

第 6.10 节将 `messages` 索引数量写为 3 个，但第 6.5 节实际定义至少 4 个：群内 seq、消息幂等、任务关联、正文 trigram。

**当前实现决定**：以实际 DDL 为准；容量估算暂不作为数据库结构断言，待真实数据规模和 `EXPLAIN (ANALYZE, BUFFERS)` 验证后再修正。

## 矛盾五：消息增长年限估算

第 6.10 节给出的每日消息增量、五年行数和达到 3000 万行的年限之间算术不一致。

**当前实现决定**：不据此提前引入分区或归档表。是否分区以真实增长、查询计划和存储指标为准，另立 decision。
