# 0009：typing 与 presence 落地时撞到的三个缺口

- 日期：2026-09-14
- 状态：open
- 关联章节：`01-后端说明书.md` 第 4.6、4.7 节，WS 事件表第 729-758 行，第 7 节（版本守卫）
- 关联决定：`0006-messages-sync-contract-gaps.md`、`0007-rate-limiting-tradeoffs.md` 第四节

## 一：说明书没有定义 server→client 的 typing 事件

第 739 行定义了客户端怎么发：`typing:start` / `typing:stop`，载荷 `{groupId}`，**无 ack**，尽力而为、可丢、不落库。

但第 743-756 行的 Server→Client 表里**没有 typing 这一行**。说明书说清了怎么告诉服务端「我在打字」，却没说对端怎么知道。

**当前实现决定**：沿用同名事件转发，载荷补上 `userId`（契约里的 `typingEventSchema`）。没有 `userId`，收到的人无从知道是谁在打字——而发送者自己的 id 对发送者毫无意义，所以转发时用 `socket.to(room)` 排除自己。

若需求方希望换成一个事件（如 `typing` 带 `typing: boolean`），改动只在契约与两端的事件名，语义不变。

### 转发前的房间门禁（这一条不是取舍，是必要的）

`socket.to(room)` **无论发送者自己在不在那个房间都会投递**。所以不做检查的话，任何一个已登录用户都能往任意群里塞「某某正在输入」，而且 `userId` 是服务端从 token 取的、伪造不了，但**群是任意的**。

**当前实现决定**：转发前检查 `socket.rooms.has('group:'+gid)`。房间只由 `sync:hello` / `sync:pull` / `message:send` 加入，而这三条都已经过成员校验，所以这个检查**不花一次数据库查询**。

已做反向验证：去掉这行检查，`tests/runtime.test.ts` 里「陌生人发 typing」那条立刻变红（收到的数组非空）。

## 二：没有 presence 快照，所以前端刻意不画在线状态

`presence:updated` 已经按 4.6 实现并在服务端广播（进出各一次、多端只在集合变空时报离线、30 秒兜底扫描）。但**说明书里没有任何地方能让客户端知道「此刻谁已经在线」**：

- `sync:ready` 的载荷是 `{groups: [{groupId, lastSeq}], contractVersion}`（第 733 行），没有 presence
- 没有 `GET /groups/:gid/presence` 这类接口
- presence 只放内存、不落库（4.6 明确如此，这个取舍是对的）

后果是：刷新页面后，客户端只能等到某人**下次上下线**才知道他在线。在此之前画任何在线标记都是错的，而且错的方向很糟——**所有人都会显示成离线**，用户会以为同事都不在，而实际上他们一直连着。一个恒为假的指示器比没有指示器更有害。

**当前实现决定**：服务端广播照做（契约与事件都已就位，多端与兜底扫描有测试），**前端暂不渲染在线状态**。要补的话有三个选项，都需要需求方选一个：

| 选项 | 做法 | 代价 |
|---|---|---|
| A | 给 `sync:ready` 加一个 `online: [userId]` 字段 | 改契约；但 `sync:hello` 本来就是「连接后第一件事」，语义上正合适 |
| B | 新增 `GET /groups/:gid/presence` | 多一次请求；且内存态与 HTTP 无状态之间要约定好读的是哪个进程 |
| C | 连接后服务端主动向 `user:{uid}` 推一份快照 | 不改契约；但多一个只在连接时出现的事件，客户端要处理它与后续增量的合并 |

倾向 A：它复用了已有的握手，且客户端本来就在那个时刻等待服务端的回答。

## 三：**既有缺陷** —— 浏览器端从不发 `sync:hello`

`apps/web/src/App.tsx` 里有 `socket.on('sync:ready', ...)` 的监听，但**全仓没有任何地方 emit `sync:hello`**。连锁后果：

1. `sync:ready` 永远不会到达，那段监听是**死代码**（包括它里面的补投循环）。
2. 服务端算好并塞进 `sync:ready` 的 `contractVersion` **永远送不到前端**，说明书第 7 节要求的前端版本守卫**从未生效过**。
3. 冷启动实际上走的是 `chooseGroup` 里的 `api.history` + `sync:pull`——能工作，但与 4.3.2 描述的路径不是一回事，也意味着「不传 `sync:hello` 则收不到增量」这条约束在浏览器端是靠每次进群手动补投绕过的。

交接文档此前写的「按 `sync:hello`→`sync:pull` 冷启动」是**错的**，本轮已改正。

**这不是本轮新增功能的缺陷**，与 `0007` 第六节那条 `revoked_reason` 同类：既有代码没被真正跑过。发现方式是查「typing 为什么没到」时顺手 grep 了一遍事件名。

**待办**：要么让 `openSocket` 在连上后发一次 `sync:hello`（带上各群本地水位），把 4.3.2 的路径接通、顺便让版本守卫生效；要么明确放弃 `sync:hello` 路径、把服务端那条 fallback 分支和前端那段监听一起删掉。两者都行，但**不能像现在这样两头都留着**——留着的那一半会让人以为冷启动是按说明书走的。
