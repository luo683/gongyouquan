# 0008：已读回执的口径缺口

- 日期：2026-09-14
- 状态：open
- 关联章节：`01-后端说明书.md` 第 4.4.3、4.4.4 节，路由表第 667 行，验收表第 9 项（1631 行）
- 关联决定：`0004-groups-guards-and-archival.md`（404 与 403 的分工）、`0006-messages-sync-contract-gaps.md`

`GET /groups/:gid/messages/:mid/receipts` 的两档响应（`detail=0` 只给两个数，`detail=1` 追加 `readers[]`）在契约层早已定义好，缺的只是服务端。实现时撞到四处说明书没写死的地方。

## 一：`totalMembers` 要不要排除发送者

验收表第 9 项只钉了三条：「位点 ≥ 目标 `seq` 的成员计入；发送者本人排除；被移除成员不计入 `totalMembers`」。**「发送者本人排除」写在分子那一侧，分母只提了被移除成员。**

按字面实现，`readCount` 最多是 `totalMembers - 1`：25 人群里所有人都读完了，界面显示「已读 24/25」，而且永远停在这个数上。4.4.3 举的例子正是「已读 8/25」这种分数形式，一个永远到不了满的分母会让「全部已读」这个状态在界面上不存在。

**当前实现决定**：分母同样排除发送者。全员读完显示 `n/n`。

这一条需要需求方确认，因为它改的是用户天天看的数字。若产品侧要求分母含发送者（即「群里一共几个人」而不是「除了我还有几个人」），那么分子的口径也要跟着改，否则分数本身没有意义——两者必须一起动。

## 二：`:gid` 与消息实际所属群不一致

路径是 `/groups/:gid/messages/:mid/receipts`，两个 id 都由客户端给。说明书没说 `:mid` 不属于 `:gid` 时该怎么办。

三种可能的响应里，`403 FORBIDDEN_NOT_MEMBER` 是最差的：它等于告诉调用者「这条消息存在，只是不在你说的群里」。一个 A 群成员拿自己合法的 `gid` 去遍历 `mid`，就能靠错误码把 B 群的消息 id 空间探测出来。

**当前实现决定**：**先比对群、再问成员身份**，不一致一律 `404 NOT_FOUND`，与「这个 id 从来不存在」的响应完全相同，不可区分。

注意这与同一份说明书第 1642 行不冲突：那条讲的是**非成员读消息**返回 403，前提是路径本身诚实。这里的顺序是先判路径诚实性，路径不诚实时根本不进入成员判定。

## 三：系统消息没有发送者可排除

`messages.sender_id` 可空（契约里 `senderId` 是 `nullable()`，注释写明 null = 系统 / 机器人消息）。排除发送者的条件若写成 `user_id <> $2`，`$2` 为 NULL 时整个表达式是 NULL 而不是 true——**每一行都被过滤掉**，一个四人群的系统通知会报「已读 0/0」。

不报错、不抛异常，只是安静地给一个看起来合理的数字。这正是 `0007` 第六节那条 `revoked_reason = logout` 的同类陷阱：SQL 语义错了，但只有真的拿系统消息跑过才会发现。

**当前实现决定**：三处比较全部用 `IS DISTINCT FROM $2::bigint`。NULL 读作「没有发送者需要排除」，于是全群计入分母——这也符合语义：一条没有人发的通知，不存在「自己读自己」这回事。

`tests/integration/receipts.test.ts` 里有一条专测系统消息的用例，并且做过反向验证：把 `IS DISTINCT FROM` 换回 `<>`，该用例立刻以 `expected +0 to be 4` 失败。

## 四：撤回的消息还能不能查回执

说明书没提。位点模型下这是可查的：某人读到 `seq=100` 是既成事实，那条消息后来被撤回不改变他读过。

**当前实现决定**：可查，不做特殊处理。撤回后的消息在历史里仍有留痕行（4.3.6），回执挂在同一行上语义自洽。

若产品侧认为撤回应当连「谁读过」一起抹掉，那是一个额外的删除动作，需要在撤回事务里清 `read_positions`——但位点是按群而不是按消息存的，**清不掉**，只能在前端不展示。这一点在动手前要先说清楚。
