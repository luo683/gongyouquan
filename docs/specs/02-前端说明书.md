## 1. 概览与全局约定

### 1.1 形态：一套代码，两种宿主

```
                    ┌─────────────────────────────────────┐
                    │  apps/web  (React 19 + AntD + Vite) │
                    │  业务代码 100% 共用                  │
                    └──────────────┬──────────────────────┘
                                   │  只在这一层分叉
                    ┌──────────────┴──────────────────────┐
                    ▼                                     ▼
        ┌───────────────────────┐            ┌───────────────────────┐
        │ Electron 桌面版        │            │ 浏览器版               │
        │ window.desktop 由      │            │ window.desktop 由      │
        │ preload 注入（真实现）  │            │ desktopShim 注入（降级）│
        └───────────────────────┘            └───────────────────────┘
```

**唯一的差异点是 `window.desktop` 这个接口**（第 8 节）。业务代码只允许通过它访问原生能力，**不允许出现 `if (isElectron)` 这类判断散落在组件里**——一旦允许，两条路径的行为会漂移，而浏览器版只有在别人用的时候才会暴露出问题。

**判定方式**：`window.desktop.isDesktop === true`，但**只在适配层内部使用**，组件不许读它。

|---|---|---|---|

**为什么不用 Next.js**：这是个纯客户端应用，后端是独立的 Fastify 服务。Next.js 的 SSR / RSC / 文件路由在这里全是净负担，而且它会诱导人把数据获取放到服务端——但我们的数据全在自建后端，没有这个必要。

**为什么富文本输入自研**：我们只需要"纯文本 + @提及 + 换行"。引入 Slate/Draft 会带来一套自己的数据模型、序列化格式、以及粘贴/输入法（IME）处理的坑——而这些编辑器在**中文输入法下的组合输入（composition）行为**是历史重灾区。50 人的内部工具不需要 Markdown 富文本。**这个决定牺牲了"加粗/列表"这类能力，换来的是不用处理富文本编辑器的输入法地狱。**

### 1.3 全局约定

| 项 | 约定 | 理由 |
|---|---|---|
| **ID 是字符串** | 后端册 1.3 已定：`BIGINT` 主键在 JSON 中序列化为字符串。前端**所有类型定义里 ID 都是 `string`**，禁止 `Number(id)` | JS 的 `Number` 只有 53 位安全整数，`BIGINT` 直传会静默丢精度。前端如果把 ID 当数字处理（比如做数值比较、排序），会在某个 ID 超过 `2^53` 之后出现难以复现的错乱。**这是必须先立规矩的地方** |
| 时间 | 一律用 `dayjs` 解析 ISO 8601 带时区字符串；展示时转本地时区；不自己拼时间字符串 | |
| 请求 | 唯一入口 `lib/http.ts`（fetch 封装），含：access token 注入、401 自动刷新与重放、429 倒计时、错误码映射。**组件不许直接 `fetch`** | |
| 出参校验 | 每个响应过 `schema.parse`（来自 contracts）。失败时**用 ErrorBoundary 隔离该区域**并上报，不整页白屏 | 后端册第 7 节四道防线的第 1 道在前端的落点 |
| 错误文案 | `errorCode → i18n key` 的映射集中在 `lib/errorMessages.ts`，**后端返回的英文 `message` 不直接展示给用户** | 后端不承担 i18n（后端册 1.3） |
| 权限判断 | 用服务端下发的 `myPermissions` 控制按钮显隐。**前端不复制权限矩阵** | 后端册 3.4 的矩阵是唯一真源；前端复制一份必然与后端漂移 |
| 日志 | 生产环境不 `console.log`；错误上报带上 `requestId` | 排障靠 requestId 串联 |
| 埋点 | M1 不做 | 内部工具，本地日志足够 |

**关于"前端不复制权限逻辑"的落实方式**：权限相关的 UI 判断只允许出现在两个地方——服务端 `myPermissions` 字段的读取，以及一个薄封装 `usePermission(...)`。禁止在组件里写 `user.role === 'admin' && ...` 这类判断。原因是：权限规则一定会变（比如"管理员不能验收自己提交的任务"，后端册 3.5），如果前端也有一份，改的时候一定会漏一处，而漏掉的后果是**按钮显示了但点下去报 403**——用户看到的是"这软件坏了"。

## 2. Electron 进程架构与安全

### 2.1 三个进程的职责

| 进程 | 职责 | **不允许做的事** |
|---|---|---|
| **main**（主进程） | 创建窗口、托盘、系统通知、开机自启、未读角标、`safeStorage` 凭证读写、自动更新、IPC 服务的服务端 | 不访问数据库、不发业务 HTTP 请求、不写业务逻辑 |
| **preload** | 用 `contextBridge` 把一组**枚举好的**能力暴露成 `window.desktop`；做参数校验与协议白名单 | 不暴露 `ipcRenderer` 本身，不暴露 Node 模块 |
| **renderer**（渲染进程） | 全部业务逻辑与 UI；通过 `window.desktop` 访问原生能力 | 不直接访问文件系统、不 `require`、不读 `process` |

**为什么不让渲染进程碰 Node**：渲染进程要渲染用户输入的文本（消息正文、文件名、群名）。一旦它能访问文件系统或执行命令，一个 XSS 漏洞就直接升级为"远程代码执行"。**把 Node 能力关在渲染进程之外，XSS 的最坏后果就只是"在页面里执行脚本"，而不是"在用户电脑上执行任意代码"。** 这是 Electron 安全的基本盘，不是可选项。

### 2.2 安全配置（`BrowserWindow` 的每一项都要有理由）

```ts
// apps/desktop/src/main/window.ts
const win = new BrowserWindow({
  width: 1280, height: 800, minWidth: 1000, minHeight: 640,
  show: false,                        // ready-to-show 后再显示，避免白屏闪烁
  webPreferences: {
    preload: path.join(__dirname, 'preload.js'),

    contextIsolation: true,           // ★ 必须。渲染进程与 preload 的 JS 上下文隔离
    nodeIntegration: false,           // ★ 必须。渲染进程拿不到 require / process
    sandbox: true,                    // ★ 渲染进程跑在 Chromium 沙箱里
    webSecurity: true,                // ★ 不许关（见下表）
    allowRunningInsecureContent: false,
    experimentalFeatures: false,
    spellcheck: false,                // 内部工具，关掉省内存
    // 不给 remote module（Electron 12+ 已移除，这里明确记录：不要引入 @electron/remote）
  },
});
```

**每一项为什么要这么设（把理由写下来，否则后来的人会为了"方便"改掉）**：

| 配置 | 如果改错的后果 |
|---|---|
| `contextIsolation: true` | 设为 `false` 后，页面里的脚本与 preload 共享全局对象，页面脚本可以**篡改 preload 暴露的函数**，或读到 preload 的闭包变量。这会让"通过 preload 白名单限制能力"的设计完全失效 |
| `nodeIntegration: false` | 设为 `true` 后，页面里能 `require('child_process')`。**任何 XSS 直接变成 RCE**。这是最常被"为了让某个库能跑"而打开的开关，也是代价最大的一个 |
| `sandbox: true` | 关闭后渲染进程以更高权限运行；配合其他配置泄漏时后果更严重 |
| `webSecurity: true` | 关闭会禁用同源策略，跨域请求不再受限、`file://` 可读取任意本地文件。**"开发时跨域麻烦"绝不构成关闭它的理由**，跨域用 Caddy 或 Vite proxy 解决 |
| 不给 `@electron/remote` | 它把主进程对象直接暴露给渲染进程，等于把 `nodeIntegration: true` 换个方式打开 |

**除 `webPreferences` 外，还必须做四件事**：

| # | 措施 | 实现 | 防 |
|---|---|---|---|
| 1 | **只加载本地打包的 renderer** | 生产环境 `loadFile(dist/index.html)`；**不 `loadURL` 远程地址** | 远程内容被篡改 / 中间人注入 |
| 2 | **禁止导航与新窗口** | `webContents.on('will-navigate', e => e.preventDefault())`；`setWindowOpenHandler(() => ({action: 'deny'}))` | 消息里的链接把整个应用窗口导航到外部页面（此时该页面就获得了 preload 能力） |
| 3 | **CSP** | `index.html` 的 meta 或 `session.defaultSession.webRequest.onHeadersReceived` 注入：`default-src 'self'; img-src 'self' data: blob: https:; connect-src 'self' https://<API域名> wss://<API域名>; script-src 'self'; style-src 'self' 'unsafe-inline'` | 内联脚本注入。`style-src` 的 `unsafe-inline` 是 AntD 运行时样式所必需，是**刻意的例外**，记录在此以免被当成疏漏 |
| 4 | **外链走系统浏览器** | `window.desktop.system.openExternal(url)`，主进程侧**校验协议白名单 `http:` / `https:`** | 消息里构造 `file://` 或自定义协议链接，点了启动本地程序 |

### 2.3 IPC 通道清单（`window.desktop` 的完整定义）

**preload 只暴露下面这些，一个不多。** 任何新增能力都要走这个清单并写进本册。

```ts
// apps/desktop/src/preload/index.ts —— 暴露面即攻击面，保持最小
contextBridge.exposeInMainWorld('desktop', {
  isDesktop: true,

  // —— 凭证（第 8 节的适配层靠它区分桌面/浏览器）——
  credentials: {
    get:    (): Promise<{ refreshToken: string } | null> => ipc.invoke('cred:get'),
    set:    (rt: string): Promise<void>              => ipc.invoke('cred:set', rt),
    clear:  (): Promise<void>                        => ipc.invoke('cred:clear'),
  },

  // —— 未读角标（数字由渲染进程聚合，主进程只负责画）——
  badge: {
    set: (count: number): void => ipc.send('badge:set', count),   // 主进程侧限幅 0-99，>99 显示 99+
  },

  // —— 桌面通知 ——
  notify: {
    show:    (n: { title: string; body: string; silent?: boolean }): void => ipc.send('notify:show', n),
    onClick: (cb: (p: { groupId: string; messageId: string }) => void): (() => void) => {
      const h = (_e: unknown, p: any) => cb(p);
      ipc.on('notify:clicked', h);
      return () => ipc.off('notify:clicked', h);      // 返回取消订阅，避免热更新后重复注册
    },
  },

  // —— 开机自启 ——
  autostart: {
    get: (): Promise<boolean>        => ipc.invoke('autostart:get'),
    set: (on: boolean): Promise<void> => ipc.invoke('autostart:set', on),
  },

  // —— 窗口 ——
  window: {
    hide:           (): void => ipc.send('win:hide'),
    setAlwaysOnTop: (on: boolean): void => ipc.send('win:alwaysOnTop', on),
  },

  // —— 应用信息与更新 ——
  app: {
    getVersion: (): Promise<string> => ipc.invoke('app:version'),
  },
  updater: {                                          // M2
    check:   (): Promise<{ available: boolean; version?: string }> => ipc.invoke('upd:check'),
    install: (): void => ipc.send('upd:install'),
  },

  // —— 系统集成（必须做协议白名单）——
  system: {
    openExternal: (url: string): void => ipc.send('sys:openExternal', url),
    showItemInFolder: (p: string): void => ipc.send('sys:showItem', p),
  },
});
```

**三条实现约束**：

1. **`ipc.invoke`（有返回值）vs `ipc.send`（无返回值）的选择**：需要结果的用 `invoke`，纯通知用 `send`。不要为了统一全用 `invoke`——那会让主进程为通知类操作也构造响应，多余且容易漏 `return` 导致渲染进程挂起。
2. **主进程必须校验参数**。渲染进程传来的数据不可信（它渲染用户输入，是 XSS 的主要目标）。特别是 `sys:openExternal` 必须校验 `new URL(url).protocol` 在 `['http:', 'https:']` 内；`cred:set` 必须校验是字符串且长度合理。
3. **`notify.onClick` 返回取消订阅函数**。热更新（开发期）时组件会重复挂载，不返回取消函数会累积监听器，导致点一次通知触发 N 次跳转。

### 2.4 主进程的托盘与窗口生命周期

| 行为 | 规则 | 理由 |
|---|---|---|
| 关闭窗口 | **隐藏到托盘**，不是退出。首次关闭时弹一次提示 | 办公软件关掉窗口就退出，会导致漏消息 |
| 真正退出 | 托盘右键菜单"退出"，或设置页"退出应用" | 用 `app.isQuitting` 标志区分：`win.on('close')` 里判断该标志决定 `hide()` 还是放行 |
| 托盘角标 | Windows 用 `win.setOverlayIcon`（需预渲染 0-99 的 PNG 到资源目录）；macOS 用 `app.dock.setBadge`；Linux 用托盘 tooltip 兜底 | 三平台 API 不同，都要处理，否则某个平台完全看不到未读 |
| 开机自启 | `app.setLoginItemSettings({ openAtLogin, args: ['--hidden'] })`；带 `--hidden` 时启动只进托盘不显示窗口 | 开机弹窗会让人立刻关掉自启 |
| 窗口位置 | 持久化到 `userData/window-state.json`，恢复时校验是否在可见屏幕内 | 否则外接显示器拔掉后窗口会出现在屏幕外，看起来像"打不开" |
| 单实例 | `app.requestSingleInstanceLock()`，第二次启动时激活已有窗口 | 多开会造成同账号多份未读状态 |

## 4. 状态管理

### 4.1 分工：Zustand 管"流"，TanStack Query 管"资源"

这个划分不是风格偏好，而是由**数据的更新方式**决定的：

| 数据 | 更新方式 | 放哪 | 理由 |
|---|---|---|---|
| 消息流 | **服务器主动推送**（WS），持续增量 | **Zustand**（`chatStore`） | TanStack Query 的模型是"请求 → 缓存 → 失效重取"，它没有"服务器主动往缓存里追加一条"的语义。硬要用的结果是每次都要 `setQueryData` 手工追加，还要自己处理去重与顺序——那不如直接自己管 |
| 群列表 / 成员 / 任务 / 评论分页 / 搜索结果 / 统计 | 请求-响应，可失效重取 | **TanStack Query** | 这些天然匹配"某个 key 的数据可能过期，重新拉一次就对"的模型 |
| 同步游标（`syncedSeq` / `pendingNew` / `eventBuffer`） | 客户端本地状态机 | **Zustand**（`syncStore`） | 纯客户端概念，服务端不存 |
| 未读聚合 / presence | 从消息流与 WS 事件派生 | **Zustand** | 派生自 `chatStore` 与 `read:updated` |
| 当前群 / 右栏 tab / 抽屉开关 / 输入草稿 | 纯 UI | **Zustand**（`uiStore`） | |

**一条硬规则：消息数组永远不在 TanStack Query 的缓存里。** 理由见上表第一行。如果哪天发现有人在 `queryClient.setQueryData(['messages', gid], ...)` 里追加消息，那是设计被破坏的信号——**消息流只允许 `chatStore` 持有**。

### 4.2 消息流的单一写入口

```
WS 事件 ──► eventBus（单一 socket 实例 + 类型化 emitter）
              │
              ├─► chatStore.applyMessage(msg)          ← 消息的唯一写入口
              │     规则 1：按 id 去重（byId 里已存在则跳过）
              │     规则 2：命中本地乐观消息（senderId + clientMsgId）→ 原地替换，保留视图位置
              │     规则 3：seq 连续 → 直接插入；出现断层（seq > syncedSeq+1）→ 触发补投，
              │              该消息进 syncStore.pendingNew
              │     规则 4：更新未读（仅当"当前群 ≠ 该消息所属群"或"窗口未聚焦"）
              │
              ├─► TanStack Query 失效（只针对资源型数据，不碰消息）
              │     task:changed     → invalidate ['tasks', groupId] + setQueryData ['task', taskId]
              │     task:comment:new → invalidate ['taskComments', taskId]
              │     group:changed    → invalidate ['groups'] + ['group', groupId]
              │     read:updated     → setQueryData ['groups']（更新该群 unreadCount）
              │
              └─► 副作用：桌面通知（mention:new / 与我相关的 task 事件）、
                        托盘角标（未读总数变化）、窗口未聚焦时闪托盘
```

**冲突消解原则（写进代码注释）**：同一个实体不能被两个来源同时写。

| 数据 | 唯一写入来源 |
|---|---|
| 消息（新增/编辑/撤回） | WS 事件（含补投结果） |
| 历史分页结果 | REST `GET /groups/:gid/messages` → **合并进 `chatStore`，不另存一份** |
| 任务 | TanStack Query（WS 只负责触发 invalidate） |

历史分页与实时流合并的具体做法：两者都调用 `chatStore.upsertMessages(list)`，store 内部按 `id` 与 `seq` 去重后插入有序数组。这样"REST 分页结果覆盖了刚推来的新消息"这类问题从设计上不存在。

### 4.3 `chatStore` 的数据结构

**要求**：虚拟列表需要 `index → message` 的 O(1) 查找，去重需要 `id → message` 的 O(1) 查找，同步状态机需要按 `seq` 定位。

```ts
type GroupMessages = {
  byId:        Map<string, MessageDTO>;   // id → 消息（去重、编辑、撤回）
  seqToId:     Map<number, string>;       // seq → id（断层检测、按 seq 定位）
  sortedSeqs:  number[];                  // 升序 seq 数组（虚拟列表的 count 源）
  clientToId:  Map<string, string>;       // clientMsgId → id（乐观消息转正）
};

// chatStore
{
  groups: Map<string, GroupMessages>;     // groupId → GroupMessages
  upsertMessages(groupId, list): void;    // 唯一写入口（实时流与历史分页都走它）
  markEdited(groupId, msg): void;
  markDeleted(groupId, msg): void;
  reset(groupId): void;                   // 退出登录时清空
}
```

**为什么 `sortedSeqs` 用数组而不是每次排序**：50 人群、缓存 5000 条消息时，每次插入都 `sort()` 是 O(n log n)，而滚动时会频繁读取。数组 + 二分插入（O(n) 但常数极小，且 n 上限受缓存策略约束）足够；**更关键的是它让虚拟列表的 `getItem(index)` 变成 O(1)**，这是渲染流畅的前提。

**缓存上限**：每个群最多保留 **2000 条**消息（首屏 50 条 + 向前翻页累积）。超出时从数组头部丢弃，同时从 `byId`/`seqToId` 删除，并把 `oldestLoadedSeq` 前移——向前翻页时用 `beforeSeq = oldestLoadedSeq` 继续拉。**不做无限累积**：5000 条以上的 DOM 数据会让内存与 GC 压力上升，而用户极少回翻到那么远（真要看更早的，用搜索定位）。

### 4.4 客户端同步状态机（与后端册 4.3 成对，必须一起改）

> **这一节是前端册最重要的一节。** 后端册 4.3 定义了服务端的契约（`sync:pull` 返回 `asOfSeq`、补投返回最新状态而非重放事件），本节定义客户端如何消费它。**两边改动必须同步**——只改一边会让"不丢消息"的保证失效，而这种失效只在弱网下暴露。

#### 4.4.1 per-group 的同步状态

```ts
type GroupSyncState = {
  syncedSeq:    number;         // 已连续应用到的 seq；服务端权威值为准
  pulling:      boolean;        // 是否有一次补投在飞行中
  pendingNew:   MessageDTO[];   // 因断层暂存的新消息（seq > syncedSeq + 1）
  eventBuffer:  ServerEvent[];  // 补投期间收到的更新/删除事件（绝不丢弃）
  oldestLoadedSeq: number;      // 本地最老的一条（向前翻页用）
};
```

#### 4.4.2 冷启动与重连流程

```
App 启动 / WS 重连成功
  1. 从本地缓存读 syncedSeq（M2 的 IndexedDB；M1 从 0 开始）
  2. emit('sync:hello', { groups: [...{groupId, syncedSeq}] })
  3. 收 sync:ready → { groups: [{groupId, lastSeq}], contractVersion }
     · contractVersion 与本地不一致 → 全局提示"客户端版本较旧，建议升级"（不阻断）
  4. 对每个 lastSeq > syncedSeq 的群，串行发起补投（见 4.4.3）
     · 并行也会对，但串行能让"最活跃的群"先补齐，体验更好
  5. 补投全部完成 → pulling 状态清空 → 排空 pendingNew 与 eventBuffer
```

#### 4.4.3 补投循环

```ts
async function pullGroup(groupId: string) {
  const st = syncStore.get(groupId);
  if (st.pulling) return;
  st.pulling = true;
  try {
    let since = st.syncedSeq;
    for (;;) {
      const res = await socket.emitWithAck('sync:pull',
        { groupId, sinceSeq: since, limit: 200 });

      chatStore.upsertMessages(groupId, res.items);

      // ★ 无条件推进到服务端给的 asOfSeq，不做"必须连续"的判断
      since = res.asOfSeq;
      syncStore.set(groupId, { syncedSeq: res.asOfSeq });

      if (!res.hasMore) break;
      await yieldToMain();       // 让出一帧，避免大页补投卡住 UI
    }
  } finally {
    st.pulling = false;
    drainBuffers(groupId);        // 排空 pendingNew + eventBuffer
  }
}
```

**为什么是无条件推进（这一条与后端册 4.3.3 是同一个决定的另一半）**：`seq` 会因事务回滚留下**永久空洞**。客户端如果按"必须连续"来设计（收到 106 而本地是 104 就认为"我缺 105，等它来"），会**永久卡死在这个群上**。`sync:pull` 的结果就是服务端的权威答案——105 不在结果里，说明它不存在。客户端不需要也无法区分"回滚的空洞"和"我没收到"，**只能相信补投结果**。

**排空缓冲的顺序不能颠倒**：

```ts
function drainBuffers(groupId: string) {
  const st = syncStore.get(groupId);

  // 1. 先按 seq 升序排空 pendingNew（它们是被断层挡住的新消息）
  const pend = st.pendingNew.sort((a, b) => a.seq - b.seq);
  for (const m of pend) {
    if (m.seq > st.syncedSeq + 1) { /* 仍有断层：再触发一次补投，本消息留在缓冲 */ break; }
    chatStore.upsertMessages(groupId, [m]);
  }

  // 2. 再按到达顺序排空 eventBuffer（更新/删除）
  for (const ev of st.eventBuffer) {
    applyEventIfNewer(ev);      // 比较 updatedAt，只有更新鲜才覆盖
  }
  st.eventBuffer = [];
}

// 应用更新/删除时的单调性判断——防止乱序事件造成状态回退
function applyEventIfNewer(ev: { message: MessageDTO }) {
  const local = chatStore.getById(ev.message.groupId, ev.message.id);
  if (!local) return;                                   // 本地没有：等补投带过来
  if (new Date(ev.message.updatedAt) <= new Date(local.updatedAt)) return;  // 旧事件，忽略
  chatStore.upsertMessages(ev.message.groupId, [ev.message]);
}
```

**为什么更新/删除事件要存进 `eventBuffer` 而不是直接应用**：补投是一次网络往返，期间实时事件可能先到。如果直接应用，会出现"删除事件先到、目标消息还没补投回来"→ 找不到目标 → 丢弃删除 → **客户端永久显示一条本该消失的消息**。缓冲 + 补投完成后按 `updatedAt` 单调应用，能同时解决乱序与"目标未到"两个问题。

#### 4.4.4 实时事件的入口判定

```ts
function onMessageNew(m: MessageDTO) {
  const st = syncStore.get(m.groupId);

  if (m.seq <= st.syncedSeq) return;              // 重复投递：按 id 去重后丢弃

  if (st.pulling || m.seq > st.syncedSeq + 1) {
    st.pendingNew.push(m);                        // 补投中或有断层：暂存
    if (!st.pulling) pullGroup(m.groupId);        // 有断层且没在补投 → 主动补
    return;
  }

  chatStore.upsertMessages(m.groupId, [m]);       // seq == syncedSeq + 1：直接应用
  syncStore.set(m.groupId, { syncedSeq: m.seq });
}

function onMessageUpdated(m: MessageDTO) {
  const st = syncStore.get(m.groupId);
  if (st.pulling) { st.eventBuffer.push({ type: 'updated', message: m }); return; }
  applyEventIfNewer({ message: m });
}
// onMessageDeleted 与 onMessageUpdated 完全同构（都用 upsertMessages + updatedAt 比较），
// 因为后端册 4.3.4 要求删除事件也携带完整 DTO —— 这正是不必区分两者的原因
```

#### 4.4.5 WS 不可用时的降级

公司网络可能屏蔽 WebSocket（代理不支持 `Upgrade`）。降级策略：

```
socket 连续重连失败 3 次（指数退避，上限 30s）
  → 切换到 HTTP 轮询模式：
     · GET /groups/:gid/sync?sinceSeq= 每 5 秒拉一次（仅对当前打开的群）
     · 未读与新任务用 GET /groups 与 GET /me/tasks 每 30 秒轮询
     · 顶部显示"实时连接不可用，已降级为轮询"的持久提示（不隐藏，让用户知道为什么消息会延迟）
  → 同时继续在后台尝试 WS 重连（每 60 秒一次）
     · 成功后切回 WS，并立即走一次补投（避免轮询期间漏掉的消息丢失）
```

**降级期间发消息走 HTTP** `POST /groups/:gid/messages`（后端册 5.4 已提供）。**幂等键 `clientMsgId` 必须复用**——降级期间重试概率更高，如果每次重试生成新 UUID，会产生重复消息。

### 4.5 乐观发送与失败重试

```
用户回车
  1. 生成 clientMsgId = crypto.randomUUID()（★ 必须在重试期间保持不变，见下）
  2. 本地插入乐观消息：
       { id: `tmp:${clientMsgId}`, seq: null, status: 'sending', body, sender: me, createdAt: now }
     视图立刻显示（半透明 + 时钟图标）
  3. emit('message:send', {...}) 等待 ack
  4a. ack 成功 → 用返回的 {id, seq, createdAt} 原地替换（保持数组位置，避免视觉跳动），status: 'sent'
  4b. 超时 10s 未 ack → status: 'failed'，显示重试按钮
      · 重试仍用同一个 clientMsgId
  4c. 收到 message:new 且 clientMsgId 命中本地 tmp → 直接替换
      （覆盖"ack 丢了但服务端其实写成功了"的情况——这正是幂等键存在的意义）
```

**三条实现要点**：

1. **`clientMsgId` 在整条消息的生命周期内唯一且不变。** 它由"用户按下回车"这一刻生成，重试、降级切换、401 后重放——全部复用同一个值。**只有用户点"重新编辑"或修改了内容才生成新的。** 后端册 5.4 把 `clientMsgId` 定为必填，就是为了让这条契约可强制。
2. **替换时保留数组位置**。乐观消息与最终消息的 `seq` 不同，若按 `seq` 重排会让消息"跳"到另一个位置。做法是：`upsertMessages` 识别出 `clientMsgId` 命中本地 tmp 时，**在原索引处替换**，而不是删除后按 `seq` 插入。
3. **失败的消息不自动重试**（不搞指数退避自动重发）。理由是自动重发在"网络时断时续"时会堆积多条重复消息的发送尝试，而用户看到"发送失败 + 重试按钮"并自己决定更可控。**唯一例外**是 401 → 刷新 token 后重放（那是同一个请求的重放，不是新请求）。

### 5.2 消息气泡的渲染要点

| 消息类型 | 渲染 | 要点 |
|---|---|---|
| `text` | 纯文本 + @高亮 + URL 自动链接 | **绝不 `dangerouslySetInnerHTML`**（5.5） |
| `image` | 缩略图（固定最大宽高，点击开灯箱）| 缩略图先出，原图按需加载 |
| `file` | 文件名、大小、下载按钮 | 文件名是用户输入 → 纯文本渲染 |
| `system` | 居中灰字（"XX 加入了群聊"） | 不显示头像与气泡 |
| `task_card` | 卡片：编号、标题、负责人、优先级、截止时间、状态徽标 | **用 `meta` 快照渲染，不回查任务接口**（后端册 6.3） |
| 自己发的 | 右侧对齐 | |
| 已撤回 | 居中灰字"该消息已撤回" | 有权限者（owner/admin）显示"查看原文"入口，走 `GET /messages/:mid/raw` |
| 已编辑 | 气泡下方小字"已编辑" | `edited_at` 非空时显示 |

**时间分隔符**：相邻消息间隔 > 5 分钟时插入时间分隔行。**注意不要在列表滚动时反复重算**——分隔符是消息行的一部分（作为虚拟列表的一行类型），随消息一起被虚拟化，而不是独立的浮层。

**@提及的渲染**：后端返回的消息 DTO 里带 `mentions: string[]`（被提及的 userId 列表）。渲染时把正文按提及用户的显示名做**分词高亮**，而不是在正文里存标记。- **为什么不存标记（如 `@[张三](123)`）**：那样正文就变成了一种需要解析的格式，会引入转义、嵌套、注入等一整套问题，而且用户改名后历史消息里的显示名就错了。分词高亮在渲染时用当前显示名解析，**代价是用户名包含特殊字符时可能误匹配**——这个代价是可接受的（内部工具，且最坏结果只是高亮多了几个字，不是安全问题）。

### 5.3 任务看板与验收区

**看板**：4 列（待接取 `pending` / 进行中 `accepted`+`in_progress` / 待验收 `submitted` / 已完成 `done`+`cancelled`）。

| 项 | 做法 | 理由 |
|---|---|---|
| 数据获取 | `GET /groups/:gid/tasks` **一次拉全量**（群内任务数量级是百），前端分列 | 4 次分列查询会让"拖拽改状态后刷新"变成 4 次请求；全量拉取的响应体在百量级也就几十 KB |
| 排序 | 默认按 `due_at ASC NULLS LAST, priority DESC`；支持切换"按创建时间" | 与后端册 6.5 里 `tasks_board` 索引的列顺序一致，避免前端排序与后端不一致 |
| 逾期标识 | `due_at < now && status ∉ {done, cancelled}` → 红框 + "逾期 N 天" | |
| 拖拽改状态 | **不做** | 拖拽的语义不明确：把卡片从"进行中"拖到"待验收"到底是"提交完成"还是"越权验收"？这些流转有不同的权限与前置条件（后端册 4.5），用按钮 + 确认更清楚。**放弃拖拽换来的是状态机语义不被绕开** |
| 卡片信息 | 编号、标题、负责人头像、优先级色条、截止时间、评论数、附件数 | `comment_count` / `attachment_count` 是后端冗余字段（后端册 6.5 的 `tasks` 表），直接用，不回查 |

**任务详情抽屉的验收区**：这是权限规则最集中的地方，前端必须严格按 `myPermissions` 显隐。

```ts
// 服务端下发的 myPermissions（后端册 5.5 GET /tasks/:tid）
type TaskPermissions = {
  canAccept: boolean;      // pending 且我是负责人
  canStart: boolean;       // accepted 且我是负责人
  canSubmit: boolean;      // (accepted|in_progress) 且我是负责人
  canReview: boolean;      // submitted 且我是 owner/admin 且【我不是本次提交者】
  canCancel: boolean;      // 非终态 且我是 owner/admin
  canReassign: boolean;    // 非终态 且我是 owner/admin
  canEdit: boolean;        // 非终态 且我是 owner/admin
};
```

**`canReview` 的判定必须来自服务端**。前端不能写成 `isAdmin && task.status === 'submitted'`——因为还差一个条件"我不是本次提交者"（后端册 3.5 第 1 条）。**这个条件前端无从得知**（需要 `task_acceptances` 里本轮 `submitter_id`），所以只能由服务端算。

**打回时必须填原因的交互**：验收弹窗里，选择"打回"时原因输入框变为必填（`Form.Item required`），提交前本地校验，同时后端也会拒（`400 INVALID_ARGUMENT`）。**本地校验是为了体验，后端校验是为了正确性，两者都要有。**

### 5.4 消息列表的虚拟滚动与滚动位置保持

> **这是聊天 UI 最容易做坏的部分。** 用户对"我在翻历史，来了条新消息，我的位置被顶走了"的容忍度是零。所以这一节写得细。

#### 5.4.1 基本结构

用 `@tanstack/react-virtual`，**反向列表**（`sortedSeqs` 升序存储，但显示时从下往上）：

```tsx
const rowVirtualizer = useVirtualizer({
  count: sortedSeqs.length,
  getScrollElement: () => scrollRef.current,
  estimateSize: () => 64,             // 估高；图片消息会实测后修正
  overscan: 8,                        // 上下各多渲染 8 行，减少快速滚动时的空白
  // 关键：列表容器用 flex-direction: column-reverse 时，
  // 需要把 measureElement 的偏移换算处理正确，否则动态高度会算错
});
```

**为什么用 `column-reverse`**：聊天界面天然是"从底部往上生长"的。用常规 `column` 布局时，插入新消息后必须手动 `scrollTop = scrollHeight`，而这个赋值在图片加载完成（高度变化）后会失效，导致"跳一下"。`column-reverse` 让浏览器原生把"新增内容在底部"处理掉，滚动位置在底部时天然稳定。

#### 5.4.2 滚动位置保持（核心逻辑）

```ts
const NEAR_BOTTOM_PX = 40;   // 距底部多少像素内算"在底部"

function onNewMessage() {
  if (isNearBottom()) {
    scrollToBottom({ behavior: 'smooth' });        // 在底部 → 跟随
    newMessagesCount = 0;
  } else {
    newMessagesCount++;                            // 在看历史 → 只计数，显示悬浮按钮
  }
}

function onMessageHeightChanged(id: string) {      // 图片加载完成、文本换行变化
  // 只有当变化发生在"视口上方"时才需要补偿偏移，否则会出现跳动
  if (isAboveViewport(id)) {
    preserveAnchor();                              // 记录锚点前先补偿 scrollTop
  }
}
```

**锚点保持的实现**：记录 `anchor = { id: 视口顶部第一条可见消息的 id, offset: 该消息顶部距视口顶部的距离 }`。当列表内容在视口上方发生插入/高度变化时，用 `scrollToIndex(anchorIndex)` 后修正 `offset`。**必须用"消息 id + 偏移"而不是"scrollTop 数值"**——因为 `scrollTop` 在内容变化时会失效。

#### 5.4.3 四种场景的正确行为

| 场景 | 期望行为 |
|---|---|
| 用户在最底部，来了新消息 | 平滑跟随到底部；不显示悬浮按钮 |
| 用户在翻历史，来了新消息 | **视口完全不动**；右下角出现"N 条新消息"悬浮按钮（点它滚到底） |
| 用户点击悬浮按钮 | 滚到底部 + 清空计数 |
| 用户向上滚动到顶（`oldestLoadedSeq` 之前） | 触发 `GET /groups/:gid/messages?beforeSeq=oldestLoadedSeq`，**加载后保持视口位置**（新内容插在视口上方，必须补偿偏移，否则会跳） |
| 从搜索结果 / 引用消息跳转到某条消息 | 若该 `seq` 不在本地 → 先拉取该消息为中心的窗口（`beforeSeq = seq + 25`），再滚动定位 + 高亮 2 秒 |
| 切换群 | 滚到该群上次离开的位置；没有记录则滚到底部 |

**注意"切换群"这一条**：每个群要记住自己的滚动位置（存 `uiStore`，按 `groupId` 索引，只在会话内存里，不持久化）。**如果切回来永远是底部，用户会失去"我刚看到哪里"的上下文**——而这在多个群之间来回切换时是高频操作。

#### 5.4.4 性能边界

| 指标 | 目标 | 说明 |
|---|---|---|
| 单群缓存消息上限 | 2000 条（4.3） | 超出丢弃最老的，`oldestLoadedSeq` 前移 |
| 同时挂载的消息 DOM | ≤ 30 行 | 由虚拟滚动保证（`overscan: 8` + 视口可见约 14 行） |
| 滚动帧率 | ≥ 50fps（1000 条消息窗口内） | 用 Chrome DevTools Performance 面板验证 |
| 一次性补投 1000 条 | ≤ 3s 且不卡 UI | 补投按 200 条一页，`yieldToMain()` 让帧 |
| 图片消息 | 缩略图 ≤ 40KB | 后端册 8.3 的压缩参数保证；前端懒加载原图，**列表里绝不加载原图** |

**"列表里绝不加载原图"是带宽约束下的硬要求**（后端册 6.10：50 人同时打开一张 3MB 原图 = 7 分钟）。缩略图 40KB × 50 人 = 2MB，1 秒内完成。这个差距是 20 倍。

### 5.5 消息渲染的安全要求（XSS 面）

**消息正文、文件名、群名、用户名、任务标题——全是用户输入。** 这是本应用最大的 XSS 攻击面。

| 规则 | 说明 |
|---|---|
| **禁止 `dangerouslySetInnerHTML`** | 全局 ESLint 规则 `react/no-danger` 设为 error。任何需要 `dangerouslySetInnerHTML` 的场景都必须先在本册新增一条设计说明并通过 code review |
| **正文按"纯文本 + 结构化提及"渲染** | `body` 当纯文本；`mentions: string[]` 里的 userId 用于分词高亮。**不在正文里存任何标记语法**（5.2） |
| **换行用 CSS** | `white-space: pre-wrap`，不把 `\n` 替换成 `<br>` |
| **URL 自动识别必须校验协议** | 只允许 `http:` / `https:`。实现用 `new URL(candidate)` 解析后判断 `protocol`，**不是正则匹配 `^https?://`**（正则能被 `java\nscript:` 之类绕过）。链接加 `rel="noopener noreferrer"`，点击走 `desktop.system.openExternal` |
| **文件名不做任何解释** | 显示为文本；下载时用 `Content-Disposition: attachment`（后端册 8.3 已保证）。前端**不允许**根据文件名后缀决定渲染方式 |
| **不引入完整 Markdown 渲染** | 代码块、加粗、列表一律不支持。理由：Markdown 渲染器（marked / markdown-it）默认允许 HTML 透传，是 XSS 的高发入口，而内部工具不需要这些格式 |
| **@选择器与输入框** | 自研轻量层（1.2）。输入框内部是 `contenteditable`，但**提交时只提取纯文本 + 提及 id 列表**，不提交 HTML。粘贴富文本时取 `text/plain`（`e.clipboardData.getData('text/plain')`），**不要 `text/html`** |
| **附件预览** | 图片预览用 `blob:` URL（从签名 URL 拉取后 `URL.createObjectURL`），用完 `revokeObjectURL`。**不用 `data:` URL 渲染大图**（会撑爆内存） |

**一条容易漏的**：群名、用户名、任务标题在"标题栏 / 面包屑 / 通知内容"里出现时，同样不能进 HTML。桌面通知的 `body` 是纯文本（Electron 的 `Notification` 不解析 HTML），但**要注意通知内容里的换行与长度截断**，避免一条超长消息把通知撑满屏幕。

### 5.6 图片与附件的交互

| 交互 | 实现 | 注意 |
|---|---|---|
| 粘贴图片 | 渲染进程 `paste` 事件取 `clipboardData.files` | ⚠️ **必须归一化**：Windows 剪贴板常给 `image/bmp`，而后端白名单不含 BMP（后端册 8.3）。做法是先把图片画到 `<canvas>`，再用 `canvas.toBlob('image/png', 0.9)` 转成 PNG 后上传 |
| 拖拽上传 | `ondrop` 取 `dataTransfer.files`；拖拽悬停时显示全屏提示层 | 要 `e.preventDefault()` 在 `dragover` 上，否则浏览器会直接打开该文件 |
| 上传流程 | `POST /files` → 得到 `fileId` → `POST /files/:fid/complete` → 拿到 `ready` 后才发消息 | **不要在 `ready` 之前发消息**：消息引用了未完成的文件，对方下载会 404 |
| 上传进度 | 用 `XMLHttpRequest.upload.onprogress`（`fetch` 无上传进度） | 这是唯一需要放弃 `fetch` 的地方，单独封装 |
| 大文件 | M1 上限 50MB，**不做分片** | 50MB 在公司内网上传约 10-30 秒，可接受；分片会引入断点续传、分片合并、过期清理一整套复杂度 |
| 下载 | 走 `GET /files/:fid/url` 拿 302 → 用 `desktop.system.openExternal` 交给浏览器 | **不让 Electron 自己下载**：省去下载管理 UI、进度、取消、断点等一整套功能 |
| 图片灯箱 | 点击缩略图打开全屏查看，支持左右切换同一条消息的多个图片、ESC 关闭 | 用 AntD `Image.PreviewGroup`，不自己写 |

## 6. 跨群「我的任务」

`GET /me/tasks`（后端册 6.7）是单人视角下的刚需——一个用户可能在 6 个群里，按群看任务意味着每天切 6 次才知道自己要干什么。

**入口**：左侧栏 `MyTasksEntry`，带"待我处理"的徽标数。

**视图设计**：

| 分组 | 包含 | 为什么这样分 |
|---|---|---|
| **需要我动作** | 我负责且状态 ∈ {`accepted`, `in_progress`}；我负责且 `submitted` 但**我不是提交者**的验收任务；`pending` 待我接取的 | 这是"我现在该干什么"的答案，放在最上 |
| **等待他人** | 我负责且已提交、等验收的 | 我做完了，等别人 |
| **有风险** | 逾期任务（任何状态）；被打回 ≥ 2 次的任务 | 需要关注但不一定要立刻动 |

**每条显示**：群名 + 任务编号 + 标题 + 状态 + 截止时间（逾期标红）+ 最近一次状态变更时间。点击 → 切到该群并打开任务详情抽屉（**跨群跳转要同时切群和开抽屉**，这是这一屏的主要交互）。

**筛选**：全部 / 仅逾期 / 仅本周到期；按群筛选。**默认筛选"仅未完成"**——已完成的任务不应该挤占这一屏。

**和统计模块的边界**：这一屏是"我的待办"，不是"我的绩效"。**不在这里显示交付数量、平均周期、打回次数这类个人统计**——那是管理员视角的数据（后端册 6.8），混进来会让这一屏带上考核意味，用户会不愿意用它。

## 7. 通知、未读与免打扰

### 7.1 未读聚合与托盘角标

**未读数据的三个来源**：

| 来源 | 数据 | 更新方式 |
|---|---|---|
| 群未读数 | `GET /groups` 返回的 `unreadCount`（**服务端限界 ≤100**，后端册 4.4.2） | 主动拉取 + `read:updated` / `message:new` 时本地增减 |
| @我未读 | `GET /me/mentions?unreadOnly=1` | 同上；红点由它驱动 |
| 任务待办 | `GET /me/tasks` 里"需要我动作"的数量 | 拉取 + `task:changed` 时失效重取 |

**角标数字的计算**：

```ts
// unreadStore
badgeTotal = min(99, Σ groups.unreadCount)   // 服务端每群封顶 100，总的再封顶 99
```

**两个注意点**：

1. **角标必须反映"未读总数"，与窗口是否聚焦无关。** 不要写成"窗口聚焦时不显示角标"——用户会把窗口放在旁边做事，角标是他回来看的线索。
2. **本地增减的口径要与服务端一致**：自己发的消息不计、`kind='system'` 不计。**最稳妥的做法是本地只做乐观增减，并在下一次 `GET /groups` 时以服务端为准覆盖。** 纯本地累加一定会与服务端漂移（编辑、撤回、补投、多端操作都会影响），所以必须有"以服务端为准"的对账时机。

**托盘角标的绘制**在 `unreadStore` 订阅里触发：

```ts
useEffect(() => unreadStore.subscribe(s => {
  desktop.badge.set(s.badgeTotal);      // 桌面版走 IPC；浏览器版走 navigator.setAppBadge
}), []);
```

### 7.2 通知触发条件（白名单，不是黑名单）

**只有下面这几类事件会触发桌面通知**，其余一律不弹（只看角标）：

| 事件 | 条件 | 通知内容 |
|---|---|---|
| `mention:new` | `notification_prefs.notify_mention = true` | 「张三 在 #项目A 提到了你」+ 消息摘要 |
| 我被指派新任务 | `notify_task = true` 且 `task:changed` 里 `assigneeId` 变成了我 | 「李四 给你指派了任务 #12：修复登录问题」 |
| 我负责的任务被评论 | `notify_task = true` 且我是 `assigneeId` | 「王五 在任务 #12 下评论」+ 摘要 |
| 我负责的任务被验收通过 / 被打回 | `notify_task = true` 且我是 `assigneeId` | 「任务 #12 已验收通过」/「任务 #12 被打回：<原因>」 |
| `system:notice` 且 `level = 'critical'` | 在系统群里 | 运维告警（见下） |
| **普通群消息** | —— | **不通知**。这是刻意的：50 人群里每个人都说话，每条都弹通知会让用户在第一小时就关掉通知权限 |

**关于运维告警的通知**：`#运维告警` 群里的 `critical` 级 `system:notice` 要弹原生通知（方案决策是"告警只进群，两人都订阅桌面通知"）。这是上面"普通群消息不通知"的一个**显式例外**，实现上按 `group.isSystem && level === 'critical'` 判定，而不是靠关键词匹配。

**判定逻辑集中在一处**（`hooks/useNotification.ts`），不允许散在事件处理里——否则"哪些事件会弹通知"这个问题的答案会分散到十几个文件，改起来必然漏。

### 7.3 节流聚合（必须做，否则通知会被关掉）

**问题**：25 人群里讨论一个话题，5 秒内可能产生 8 条消息。如果每条都弹一个原生通知，用户会立刻去系统设置里关掉这个应用的通知——**一旦被关掉，真正的 @我 也收不到了**。所以节流聚合不是"优化"，而是"让通知仍然可用的前提"。

```
窗口：5 秒，按 groupId 分组
  · 窗口内 1 条         → 「张三：<前 60 字>」
  · 窗口内 N 条 同一人  → 「张三 发了 3 条新消息」
  · 窗口内 N 条 多人    → 「张三、李四 等 3 条新消息」
窗口结束后统一发一条原生通知（不是立刻发第一条再合并）
```

**为什么要"等窗口结束再发"而不是"先发第一条，后续合并更新"**：`Notification` 对象一旦 `show()` 就无法修改内容（要 `close()` 再新建，在 Windows 上会闪烁并重复响铃）。等 5 秒再发一条，对用户是"晚 5 秒知道"，但那 5 秒里他很可能本来也没在看屏幕——**用 5 秒延迟换"不刷屏"，这个交易是划算的**。

**例外：`mention:new` 不走聚合窗口**，立即通知（延迟接受上限 1 秒）。被 @ 是明确指向我的信号，延迟它会让人以为系统坏了。

### 7.4 免打扰时段

从 `notification_prefs` 读取 `dnd_enabled` / `dnd_start` / `dnd_end` / `dnd_timezone`（后端册 DDL 已定义）。

```ts
function inDnd(prefs, now = dayjs()): boolean {
  if (!prefs.dndEnabled) return false;
  const t = now.tz(prefs.dndTimezone).format('HH:mm');
  const { dndStart: s, dndEnd: e } = prefs;

  // 必须处理跨午夜：22:00 - 08:00 是最常见的配置
  return s <= e
    ? (t >= s && t < e)        // 同日区间，如 12:00 - 14:00
    : (t >= s || t < e);       // 跨午夜，如 22:00 - 08:00
}
```

**免打扰期间的行为**：

| 项 | 行为 |
|---|---|
| 原生通知 | **不弹**（包括 @我） |
| 托盘角标 | **照常更新** |
| @我红点 | **照常显示** |
| 托盘闪烁 | 不闪 |
| 服务端 | 不受影响（服务端不管通知，`notification_prefs` 只是被前端读取的配置） |

**一个需要两册对齐的决策点（写在这里避免遗漏）**：免打扰期间要不要豁免 @我？

- 后端册定义的 `notification_prefs` 表**没有** `dnd_allow_mention` 字段。
- 我的建议是 **M1 不做豁免**：用户显式设了免打扰，@我 也静默。理由是免打扰的设置意图就是"这段时间别打扰我"，而 @我 的信息在恢复后仍能从红点与未读列表看到，不会真的丢。
- 如果实际使用中出现"设了免打扰导致错过重要 @"的抱怨，**M2 再加 `dnd_allow_mention` 字段**（走扩展-收缩迁移，加一个可空/带默认值的列，成本很低）。

**这里刻意不加字段，而不是先加上**：加了字段就必须在前端做一套开关 UI、在后端做一套校验、在契约里加字段，而"是否需要"目前是猜测。**留一个明确的扩展点比留一个没人用的开关好。**

### 7.5 已读回执的展示分级

后端册 4.4.3 定义了"聚合"与"名单"两档接口，前端按下表决定用哪档：

| 消息类型 | 默认展示 | 展开后 |
|---|---|---|
| 普通文本 / 图片 / 文件 | 聚合：「已读 8/25」 | 点击展开名单（走 `?detail=1`） |
| `task_card` | **默认展开名单** | —— |
| 命中 @我的消息 | **默认展开名单** | —— |
| 公告类（M2） | 默认展开名单 | —— |

**文案必须用"已读到此"而不是"已读"**。原因见后端册 4.4.4：位点会"追认"——某人读到 `seq=100`，意味着他也算读了 1..100，即使他其实是直接跳到最新、根本没翻到第 50 条。写"已读"是一个强断言，用户发现"他没看却说已读"时会不信任这个功能；写"已读到此"是准确的位点语义。

**性能与缓存**：

```ts
// 只为"视口内可见的消息"请求回执，不是全部消息
const visibleSeqs = useVisibleSeqs();          // 虚拟滚动已经知道哪些行可见
// 位点单调 → 回执结果只增不减 → 可以安全缓存，短 TTL 即可
useQueries(visibleSeqs.map(seq => ({
  queryKey: ['receipts', groupId, seq],
  queryFn: () => api.messageReceipts(groupId, seq, /* detail */ false),
  staleTime: 30_000,
})));
// 收到 read:updated 事件 → 只失效当前群、且 seq <= 该事件位点的回执查询
```

**`read:updated` 的失效要限定范围**，不要 `invalidateQueries(['receipts'])` 全量失效——25 人群里任何人滑动消息都会推进位点，全量失效会导致回执接口被高频重查。**只失效"位点 ≤ 新位点"的可见消息**。

### 8.2 浏览器版的四个实质差异（必须显式处理，不能靠"恰好也能用"）

| 差异 | 桌面版 | 浏览器版 | 处理方式 |
|---|---|---|---|
| **refresh token 传递** | 存 `safeStorage`，刷新时放请求体 | HttpOnly Cookie，浏览器自动携带 | **分支只出现在 `lib/http.ts` 一处**（见 8.3） |
| **通知点击跳转** | IPC 带结构化 payload（`groupId` + `messageId`） | Web Notification 的点击无法携带 payload | 桌面版精确跳转；浏览器版退化到"聚焦窗口 + 跳到最近有未读的群"。**这个降级必须写进文档**，否则会被当成 bug |
| **自动更新** | `electron-updater` | 不需要——刷新页面就是最新版 | 设置页在浏览器版显示"浏览器版随服务器自动更新"，不显示检查按钮 |
| **代理环境下的 WS** | 系统代理设置 | 受浏览器与公司代理限制，可能屏蔽 WebSocket | 4.4.5 的 HTTP 降级路径对两个版本都生效 |

**一条安全说明（不要回避）**：桌面版的 refresh token 存在本地磁盘上（`safeStorage` 用操作系统凭据加密）。这意味着**如果别人的电脑没锁屏，理论上可以提取该 token**。这是所有桌面客户端的固有属性，不是本设计的缺陷——但要在使用说明里写明，而不是假装桌面的凭证"更安全"。

### 8.3 `lib/http.ts` 里唯一的宿主分支

```ts
async function refresh(): Promise<string> {
  const isDesktop = desktop.isDesktop;

  if (isDesktop) {
    const cred = await desktop.credentials.get();
    if (!cred) throw new AppError('REFRESH_INVALID');
    const res = await rawPost('/api/v1/auth/refresh', { refreshToken: cred.refreshToken });

    // ★ 轮换：必须把新的 refresh token 存回去
    await desktop.credentials.set(res.refreshToken);
    return res.accessToken;
  }

  // 浏览器：refresh token 在 HttpOnly Cookie 里，浏览器自动带上
  const res = await rawPost('/api/v1/auth/refresh', {});
  return res.accessToken;
}
```

**轮换的正确接线是这里最容易漏的一步**：后端册 3.1 规定每次刷新都会轮换 refresh token，所以桌面版**必须把返回的新 token 存回 `safeStorage`**。如果忘了存，下次刷新仍然用旧 token → 被判定为**重用** → 整个 family 作废 → 用户被强制登出。**这个 bug 的表现是"用户每隔 30 天被莫名踢下线"，排查成本很高，所以单独点出来。**

### 8.4 浏览器版的部署形态

浏览器版就是一组静态文件（`dist/` 的产物），由 Caddy 直接托管（见 `03-AI运维手册.md`），与 API 同域：

```
https://<域名>/            → 静态文件（浏览器版）
https://<域名>/api/*       → 反向代理到 api:3000
https://<域名>/ws          → WebSocket 升级 → api:3000
https://<域名>/_files/*    → 签名 URL 的附件（Caddy 直发）
```

**必须同域**：refresh token 走 HttpOnly Cookie，跨域（不同 site）会因 `SameSite` 限制带不上，而且 CORS + 凭证的组合会引出 `credentials: 'include'`、`Access-Control-Allow-Credentials` 一整套配置。**同域部署让这些问题全部不存在。**

**前端路由用 `createHashRouter`**（`#/groups/12`）而不是 BrowserRouter：桌面版从 `file://` 加载，history 模式在 `file://` 下会断；浏览器版虽可用 history，但**两个宿主用同一套路由配置**才能保证行为一致，所以统一用 hash 路由。代价是 URL 里多一个 `#`，对内部工具完全可接受。

## 10. 契约消费与错误处理

### 10.1 请求封装的职责

`lib/http.ts` 是全应用**唯一**发起请求的地方（`components/` 与 `features/` 里禁止出现 `fetch`）。它负责：

```
请求前：
  1. 注入 Authorization: Bearer <access>（从 sessionStore 取）
  2. 注入 X-Request-Id（uuid，用于排障串联）
  3. 写请求走 Zod 入参校验（复用 contracts 的 schema，防"前端传错字段"）

响应处理：
  1. 401 TOKEN_EXPIRED → 静默刷新 → 重放原请求（★ 重放时 clientMsgId 必须复用）
  2. 401 REFRESH_INVALID / REFRESH_REUSED → 清凭证 + 跳登录 + toast
  3. 429 → 读 Retry-After，返回带冷却信息的错误给 UI 做倒计时
  4. 5xx / 网络错误 → 不弹 toast（避免断网时刷屏），改为顶部持久横幅
  5. 出参过 schema.parse（10.2）
```

**关于第 1 条的"重放"**：刷新后重放的是**同一个请求对象**。对 `POST /groups/:gid/messages` 而言，重放时携带的还是原来那个 `clientMsgId`——这正是它必须在"按下回车"时生成并保持不变的原因（4.5）。**如果重放生成新的 clientMsgId，401 场景下就会产生重复消息**，而这个场景（access token 15 分钟过期）每天都会发生很多次。

**并发刷新去重**：多个请求同时收到 401 时，**只能发起一次刷新**，其余请求等待同一个 Promise。否则会并发用同一个 refresh token 刷新，后到的那个被判定为"重用"→ 整个 family 作废 → **用户被莫名登出**。

```ts
let refreshing: Promise<string> | null = null;
function ensureFresh(): Promise<string> {
  if (!refreshing) refreshing = refresh().finally(() => { refreshing = null; });
  return refreshing;
}
```

**这一段代码是必须的，不是优化**：应用启动时会并发发起多个请求（群列表、我的任务、偏好），它们几乎同时 401，所以并发刷新是**必然发生**的场景，不是边角情况。

### 10.2 出参校验与错误隔离

```ts
const res = await http.get(apiRoutes.groupTasks.path(gid), { query });
const data = apiRoutes.groupTasks.res.parse(res);   // Zod 校验
```

**校验失败时的行为（生产环境）**：不抛到全局、不白屏。用 ErrorBoundary 把**该数据所在的区域**替换成"数据加载异常，请刷新"的占位，同时上报（带 `requestId` + 接口路径 + Zod 的 `issues`）。理由：一个字段多了或类型变了，不应该让整个客户端不可用——**用户还有聊天要用**。

**为什么不做"校验失败就用未校验数据渲染"**：那样会在下游产生 `undefined` 访问，错误出现在离根因很远的地方（比如某个嵌套组件里 `task.assignee.displayName` 报错），排查成本远高于"直接显示这块加载失败"。

### 10.3 错误码 → 交互映射

后端册 8.1 已经定义了每个 `code` 的"前端应有的行为"。前端侧的落实是**一张集中映射表** + 一条兜底：

```ts
// lib/errorMessages.ts —— 唯一的中文文案来源
```

## 11. 性能预算

**给出可测的数字，而不是"要快"**。这些数字在 M1 验收时会实际测量，超标就要优化：

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 首屏（冷启动 → 群列表可见） | 桌面 ≤ 2.5s，浏览器 ≤ 1.5s | 从进程启动/页面加载到首屏 paint |
| 切换群（缓存命中） | ≤ 150ms | 点击到消息可见 |
| 切换群（需补投 200 条内） | ≤ 600ms | |
| 滚动帧率（1000 条消息窗口） | ≥ 50fps | DevTools Performance |
| 单群缓存消息 | 2000 条（4.3） | 超出从头部丢弃 |
| 同时挂载消息 DOM | ≤ 30 行 | 虚拟滚动保证 |
| 渲染进程内存 | 空闲 ≤ 250MB；3 群 × 2000 条 ≤ 500MB | Electron `process.getProcessMemoryInfo()` |
| 补投 1000 条 | ≤ 3s 且不卡 UI | 分页 200 + `yieldToMain` |
| 图片消息 | 列表内只加载缩略图（≤ 40KB） | 网络面板确认无原图请求 |
| 发送消息（乐观显示） | ≤ 16ms（一帧内） | 本地插入的耗时 |

**已知的内存风险**：Electron 的渲染进程内存是常见痛点。两个容易失控的地方——**消息缓存不设上限**（4.3 已限 2000 条）与**图片 Blob URL 不释放**（5.6 要求 `revokeObjectURL`）。这两处的上限与释放都要在 code review 清单里。

**不做的事**：M1 不做代码分割与懒加载（内部工具，首屏 2.5s 达标即可，引入 `React.lazy` 会让状态边界复杂化）；不引 Service Worker（离线能力由 M2 的 IndexedDB 层解决，不做离线可用整个应用）。
