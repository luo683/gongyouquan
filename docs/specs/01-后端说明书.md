## 1. 概览与全局约定

### 1.1 系统边界

**做**：群聊（文本/图片/文件/@提及/引用回复/撤回/编辑/搜索）、群内任务（发布→接取→进行中→提交→验收通过或打回）、任务评论与进度汇报、未读与已读回执、统计与周报、运维告警入群。

**不做（明确排除，避免后端被反复要求加）**：语音消息、消息转发/合并转发、音视频通话、屏幕共享、文件在线预览、移动端接口适配、外部人员访问、私聊（只有群，没有 1v1）、端到端加密、LDAP/SSO。

**一次请求的边界**：所有业务数据都归属于某个 `group_id`。没有「跨群的全局资源」——任务、消息、文件、评论全部挂在群下。这条约束让权限校验可以统一成一句「你是不是这个群的成员」，是本系统最简单也最重要的设计约束。

### 1.2 术语表

| 术语 | 含义 | 备注 |
|---|---|---|
| 群 / group | 项目容器。建群 = 建项目组 | 本册中「群」与「项目」同义 |
| `seq` | **群内**消息序号，从 1 递增、严格单调 | 系统的正确性核心，见第 4 节 |
| 位点 / read position | 某用户在某群读到的最新 `seq` | 未读数与已读回执都由它派生 |
| 任务编号 / `task_no` | 群内任务序号，从 1 递增 | 与 `seq` 是两套独立分配器 |
| 卡片 / `task_card` | 任务在群消息流中的表现形式 | 复用消息表，见 6.3 |
| 打回 | 验收不通过，任务回到进行中 | 可无限次，每轮记入状态历史 |
| 自举 | 用自己的群聊软件承载自己的运维告警 | 见 `03-AI运维手册.md` |

### 1.3 全局 API 约定

| 项 | 约定 | 理由 |
|---|---|---|
| Base path | `/api/v1` | 版本进路径，未来不兼容改动走 `/api/v2` |
| 传输 | 仅 HTTPS。HTTP 一律 301 到 HTTPS | 明文聊天不可接受 |
| 鉴权头 | `Authorization: Bearer <access_token>` | 浏览器版同时接受 HttpOnly Cookie（见 3.1） |
| 时间 | 全部 `TIMESTAMPTZ`，API 层用 **ISO 8601 带时区偏移**（`2026-09-12T14:03:00+08:00`）。禁止使用本地时间字符串 | 消息顺序不依赖时间，但展示与审计需要无歧义 |
| ID 类型 | 业务主键 `BIGINT`（users/groups/messages/tasks…）在 JSON 中**序列化为字符串**；`files`/`sessions`/`group_invites` 用 `UUID` | JS 的 `Number` 只有 53 位安全整数，`BIGINT` 直传会在前端静默丢精度。**这一条不遵守会造成"偶发"的 ID 错乱，属于必踩坑** |
| 分页 | 游标分页，不用 offset。响应含 `{ items, nextCursor, hasMore }` | offset 在消息表上会随插入漂移，导致漏消息 |
| 请求 ID | 客户端可传 `X-Request-Id`，服务端写入日志与错误响应 | 排障时能把一次用户操作串起来 |
| 幂等 | 写接口支持 `Idempotency-Key` 头；消息发送另用 `clientMsgId` | 弱网重试不产生重复数据 |
| 错误包装 | 统一 `{ error: { code, message, details? , requestId } }`，HTTP 状态码语义化 | 前端可据 `code` 分支，不用解析文案 |
| 契约来源 | 所有入参与出参的 schema 定义在 `packages/contracts`，服务端**强制校验**（见第 7 节） | 两人分工下接口不一致的主要来源就是这里 |
| 语言 | 所有面向用户的文案由前端 i18n 提供；后端只返回 `code` 与英文 `message` | 避免后端承担多语言 |

## 2. 服务形态与模块划分

### 2.1 形态判定：单进程单体

**结论：一个 Node 进程，同时提供 HTTP 与 WebSocket。**

理由：

1. **2 人团队，运维面是稀缺资源**。拆成「API 服务 + WS 网关」会立刻带来：两个进程的健康检查、两套部署编排、进程间通信（WS 网关要拿到消息的权威顺序就得回查数据库或再引入消息队列）、以及"到底哪个进程挂了"的排障成本。收益（独立扩容）在 50 人规模下接近零。
2. **WS 与 HTTP 共享同一个数据访问层**是强需求：发消息既走 WS 也走 HTTP 兜底（见 4.2），两条路径必须落到同一段事务代码。同进程下这只是同一个函数的两次调用；跨进程下要么做内部 RPC，要么把逻辑下沉到存储过程，都是纯增负担。
3. **单进程是单点，但这是可接受的**：重启期间客户端自动重连 + `sync:pull` 补投，用户感知是"重新连接中"而不是丢消息。这是第 4 节存在的意义。

**明确不做**：微服务、消息队列（除 outbox 表这个轻量模式）、Redis（会话与状态都在 PG；见 2.3 末尾说明）。

### 2.2 技术清单（版本锁定）

| 类别 | 选型 | 版本 | 说明 |
|---|---|---|---|
| 运行时 | Node.js | **22 LTS** | 不用 24：22 是当前 LTS，容器基础镜像与原生模块兼容性最稳 |
| 语言 | TypeScript | 5.x，`strict: true` | 不允许 `any` 逃逸（CI 里 `tsc --noEmit` 卡住） |
| HTTP 框架 | **Fastify** | 5.x | 选它而非 Express/NestJS 的理由见表下 |
| 实时通信 | **Socket.IO** | 4.x | 内置重连、房间、ack 回调；选了它就不必自己实现心跳与 ack |
| 数据访问 | **Drizzle ORM** | 最新稳定 | 参数化查询、类型推导直接来自 schema；迁移用 `drizzle-kit generate` 产出 SQL 再由人审 |
| 校验 | **Zod** | 3.x | 同时用于 HTTP 入参、WS 事件、以及出参序列化校验 |
| 密码哈希 | **argon2id** | 通过 `argon2` 原生包 | 参数：`memoryCost=19456(19MB), timeCost=2, parallelism=1`（OWASP 推荐档） |
| JWT | `jose` | 最新 | 只用于 access token 签发/校验 |
| 日志 | **pino** | 最新 | 结构化 JSON；必须配 `redact` 屏蔽敏感字段（见 8.4） |
| 图片处理 | **sharp** | 最新 | 生成缩略图；注意它依赖原生库，Docker 基础镜像要用对 |
| 搜索客户端 | `meilisearch` | 对应服务端 v1.12 | |
| 定时任务 | `node-cron` | 最新 | 仅用于进程内小任务（outbox 消费、心跳写入）。**系统级定时（备份、巡检）不在这里，那是宿主机的活** |
| 测试 | `vitest` + `supertest` | 最新 | 单测优先覆盖第 9 节列的必测项 |
| 包管理 | pnpm workspace | 9.x | monorepo，便于 `packages/contracts` 共享 |

**为什么 Fastify 而不是 NestJS**：本项目的模块边界已经由「群」这个约束天然划清了（每个模块都是 `group_id` 上的一组操作），不需要 NestJS 那套 DI 容器与装饰器来强制分层。NestJS 的抽象在 2 人 2 周节奏下是净负担，而 Fastify 的 schema 校验与性能更直接。

**为什么不用 Redis**：需要 Redis 的典型场景在本项目都不成立——会话用 PG 表（`sessions`）、已读位点用 PG 表（`read_positions`）、在线状态放进程内存（单进程，天然一致）、outbox 用 PG 表。多一个 Redis 就多一个要监控、要备份、要限内存的组件，而它解决的问题我们没有。**如果将来真的要拆多进程**，Socket.IO 需要 Redis adapter 才能跨进程广播——这是引入 Redis 的唯一正当理由，届时再加。

### 2.3 模块清单

八个模块，每个模块内部固定三层（`route` → `service` → `repo`）。

| 模块 | 职责 | 关键点 |
|---|---|---|

**两条硬规则**：

1. **`tasks/state-machine.ts` 是唯一允许修改 `tasks.status` 的地方。** 任何其他文件直接 `UPDATE tasks SET status=...` 都算 bug——状态流转必须经过状态机，否则 `task_status_history` 会漏记，验收流与统计会失真。
2. **所有广播必须经过 `realtime/emit.ts`。** 不允许在业务代码里直接 `io.to(...).emit(...)`。理由是广播点是排查"消息为什么没收到"的唯一入口，散落各处就无法统一加计数与日志（第 4.7 节的 `broadcastMs` 指标依赖它）。

### 2.5 一次请求穿过哪些层

以「成员在任务下评论并 @ 了另一个人」为例，说明各层职责，便于两人分工时对齐：

```
HTTP POST /api/v1/tasks/:id/comments
  → route:  Zod 校验 body；GroupMemberGuard 确认请求者属于该任务所在群
  → service:
      1. 开事务
      2. 校验任务状态允许评论（done/cancelled 不允许）
      3. INSERT task_comments
      4. 解析 body 中的 @ → INSERT message_mentions（带 group_id 与派生 seq 不适用，见 6.6 说明）
      5. 更新 tasks.comment_count（同事务）
      6. INSERT outbox（同一事务，供搜索索引）★ 见下
      7. INSERT audit_logs（若涉及状态变化）
     commit
  → emit: 向 room `group:{gid}` 广播 task:comment:new
  → 返回 201 + comment DTO（经 Zod 出参校验）
```

★ **第 6 步是关键**：outbox 记录必须和业务数据在**同一个事务**里提交。这是"数据库写成功但索引写失败"这个问题的唯一干净解法（详见 6.9）。

## 3. 鉴权与权限

### 3.1 令牌方案

两段式：**access token（JWT，短命）+ refresh token（随机串，长命、可撤销、轮换）**。

| 项 | 值 | 说明 |
|---|---|---|
| access token 格式 | JWT（HS256），载荷 `{ sub, sid, iat, exp }` | `sid` = 会话 ID，用于"踢设备"时能立刻定位到会话 |
| access 有效期 | **15 分钟** | 短到能接受密钥轮换带来的失效，长到不频繁刷新 |
| refresh 有效期 | **30 天**，每次刷新后滚动续期 | |
| refresh 存储 | 表 `sessions.refresh_token_hash` 存 **sha256 摘要**，不存原文 | 数据库泄露不等于会话泄露 |
| 传输（桌面版） | refresh token 由 Electron `safeStorage` 加密后存本地；刷新时放请求体 | 桌面端没有浏览器同源 Cookie 语义 |
| 传输（浏览器版） | refresh token 放 **HttpOnly + Secure + SameSite=Lax** Cookie（路径限定 `/api/v1/auth`） | 前端 JS 读不到，降低 XSS 窃取风险；access token 放内存，不进 localStorage |

**轮换与重用检测（这是 refresh 机制里最容易漏、后果最严重的一环）**：

```
每次刷新：
  1. 查 sessions by sha256(rt)
  2. 若会话不存在 / 已撤销 / 已过期        → 401 REFRESH_INVALID，要求重新登录
  3. 若该会话已被 replaced_by 指向新会话    → 说明这是【旧 token 被重放】
        → 立刻撤销整个 family_id 下的所有会话（revoked_reason='reuse_detected'）
        → 401 REFRESH_REUSED
  4. 正常：INSERT 新会话行（同 family_id），把旧行 replaced_by 指向新行并 revoked_at=now()
```

第 3 步是防御：如果攻击者窃取了 refresh token，受害者或攻击者任一方先用，另一方再用时就会触发「整个家族作废」，两边都被踢下线——**宁可让用户重新登录，也不能让两方同时持有有效会话**。

**access token 的校验不做数据库查询**（纯 JWT 验签 + `exp`）。代价是"踢设备"后 access 在最多 15 分钟内仍可用。对内部办公系统这是可接受的取舍，写入文档避免被当成 bug。取消账号（离职禁用）同理——`disabled_at` 检查放在刷新与关键写操作上，不放在每个请求上。

### 3.2 密码与账号

| 项 | 做法 |
|---|---|
| 注册方式 | **仅邀请码**。`POST /auth/register` 必须带有效 `code`，注册成功即加入该群并消耗一次邀请次数 |
| 用户名 | 唯一（`lower(username)` 上建唯一索引，登录不区分大小写）；允许中文；长度 2-32 |
| 密码强度 | 最少 10 位，且必须包含字母与数字；不强制符号（强制符号会催生 `Passw0rd!` 这类弱密码） |
| 登录限流 | 同一 IP **5 次/分钟**；同一用户名 **10 次/小时**（两个维度都要，否则攻击者可以换 IP 打同一账号） |
| 失败响应 | 用户名不存在与密码错误**返回同一个错误码** `AUTH_INVALID_CREDENTIALS`，避免账号枚举 |
| 改密码 | 需原密码；成功后**撤销除当前会话外的所有会话** |
| 离职禁用 | `users.disabled_at` 置位。效果：不能登录、不能刷新、access 到期后失效。**消息与历史全部保留**（群聊上下文与审计需要） |
| 首个管理员 | 部署后执行 `node dist/cli/create-admin.js`。脚本一次性创建用户 + 群 + 邀请码，输出邀请码给管理员分发 |

### 3.3 权限判定模型

**只有两个 guard，全部权限都由它们派生。**

```
GroupMemberGuard(req, gid)
  → 查 req.user 是否是 groups(gid) 的有效成员（group_members.removed_at IS NULL 且 group 未归档）
  → 否：403 FORBIDDEN_NOT_MEMBER
  → 是：把 { role, groupId } 挂到 req.membership 上，供后续使用

GroupRoleGuard(['owner','admin'])(req)
  → 检查 req.membership.role 是否在允许集合内
  → 否：403 FORBIDDEN_ROLE
```

两个实现要点：

1. **两者串行使用**，`GroupRoleGuard` 依赖 `GroupMemberGuard` 已填充 `req.membership`。不要合并成一个——"不是成员"和"是成员但角色不够"必须是不同的错误码，否则前端没法给出正确提示。
2. **归档群是只读的**。`groups.is_archived = true` 时，`GroupMemberGuard` 仍放行读操作，但所有写操作（发消息、发任务、评论、上传）在 service 层拒绝，返回 `409 GROUP_ARCHIVED`。判断放在 guard 里会让"归档群还能不能看"变得含糊，所以读放行、写由 service 判。

| 操作 | 群主 owner | 管理员 admin | 成员 member |

| 查看群消息、任务、文件 | ✓ | ✓ | ✓ |
| 发消息（文本/图片/文件） | ✓ | ✓ | ✓ |
| 编辑自己的消息（15 分钟内） | ✓ | ✓ | ✓ |
| 撤回自己的消息（2 分钟内） | ✓ | ✓ | ✓ |
| **撤回他人的消息** | ✓ | ✓ | ✗ |
| 查看被撤回消息的原文 | ✓ | ✓ | ✗ |
| 发布任务 | ✓ | ✓ | ✗ |
| 编辑任务（标题/描述/优先级/截止时间） | ✓ | ✓ | ✗ |

### 3.5 任务相关的三条额外规则

这三条不在矩阵里，但必须在 `tasks` service 里显式实现，且都要有单测：

1. **验收人不能是提交者本人。** 若 `task_acceptances.submitter_id == req.user.id`，返回 `403 CANNOT_REVIEW_OWN_SUBMISSION`。没有这条，一个同时是管理员和负责人的用户可以自己发布、自己提交、自己验收，验收流程形同虚设——**这是最容易被漏、也最容易被内部人利用的一条**。
2. **负责人必须是本群有效成员。** 发布与改派时都要校验 `assignee_id` 在 `group_members` 中且未移除。否则会出现"指派给一个已退群的人"，任务永久卡在 pending。
3. **离职转交是管理员操作。** 成员被禁用（`disabled_at` 非空）时，其名下所有非终态任务（`status NOT IN ('done','cancelled')`）需要被处理。系统在禁用接口里返回这些任务的清单，要求调用方逐个指定新负责人或用 `POST /tasks/:id/reassign` 逐个改派。**不做自动改派**——自动指派给谁是个业务决定，系统猜错比让管理员多点几下更糟。

### 3.6 归档、禁用与只读的组合语义

这是三种"受限状态"叠加时的表现，容易实现得含糊，所以写死：

| 状态 | 读 | 写（消息/任务/评论/上传） | 成员管理 | 能否登录 |
|---|---|---|---|---|
| 群正常 | ✓ | ✓ | ✓ | ✓ |
| 群已归档 | ✓ | ✗（`409 GROUP_ARCHIVED`） | ✗ | ✓ |
| 用户已禁用（离职） | 被踢出所有会话，看不到任何内容 | ✗（无法登录） | — | ✗ |
| 群归档 + 用户禁用 | ✗ | ✗ | — | ✗ |

归档群保留在成员列表里（不清空 `group_members`），这样归档群的历史仍可查、统计仍能回溯。不提供"彻底删除群"接口——数据删除在内部工作系统里是高风险操作，且与"文字永久保留"的决策冲突；确有需要时由运维直接在数据库层处理，并留审计。

## 4. 核心机制（系统正确性所在）

> 本章是全册最重要的部分。全系统约 70% 的复杂度集中在消息同步的正确性上，而这类问题**很难通过 code review 发现**（代码看起来都对，只在断网、并发、休眠唤醒这些边界下才暴露）。所以本章的每条规则都要配单测，见 9.1。

### 4.1 消息顺序不能用时间戳，也不能用全局自增 ID

两个被否决的"直觉做法"，理由要说清楚，否则后来接手的人会想改回去：

| 直觉做法 | 为什么不成立 |
|---|---|
| **按 `created_at` 时间戳排序** | ① 客户端时钟不可信（用户可以改系统时间，客户端也只应传序号不传时间）；② 服务端同一毫秒内的多条消息无法定序（`TIMESTAMPTZ` 精度到微秒，但同一事务内 `now()` 返回同一值）；③ 未来若 API 多实例部署，机器间时钟有漂移 |
| **用 `messages.id`（全局自增）当游标** | 自增 ID 是**全局**的，不同群的消息 ID 交错跳跃。客户端要表达"某个群我读到哪了"就必须存一个跨群无意义的巨大数字，且无法用 `WHERE seq > X` 做索引范围扫描（因为同一个群的 ID 不连续，扫出来的大部分行属于别的群）。一旦按群分区或分表，ID 语义立刻崩坏 |

**结论**：顺序用**群内 `seq`**。它同时充当三个角色——排序依据、增量游标、断层检测信号。这是本系统最重要的一个设计决定。

### 4.2 群内 `seq` 分配器

**实现**：在发消息的同一个事务里，先原子递增群计数器，再把拿到的值写进消息。

```sql
-- 分配器函数（在 0001_init.sql 中定义，供应用调用）
CREATE OR REPLACE FUNCTION alloc_group_seq(p_group_id BIGINT)
RETURNS BIGINT
LANGUAGE plpgsql
AS $$
DECLARE
  v_seq BIGINT;
BEGIN
  UPDATE groups
     SET last_seq = last_seq + 1
   WHERE id = p_group_id
  RETURNING last_seq INTO v_seq;

  IF v_seq IS NULL THEN
    RAISE EXCEPTION 'group % not found', p_group_id USING ERRCODE = 'no_data_found';
  END IF;

  RETURN v_seq;
END;
$$;
```

应用侧（伪代码，事务边界必须完整）：

```ts
await db.transaction(async (tx) => {
  const seq = await tx.execute(sql`SELECT alloc_group_seq(${groupId})`);
  await tx.insert(messages).values({ groupId, seq, senderId, clientMsgId, kind, body });
  await tx.insert(outbox).values({ aggregateType: 'message', aggregateId: id, eventType: 'upsert', payload });
  // ↑ 同事务，见 6.9
  return { id, seq };
});
```

**必须理解的两个性质**：

**① `UPDATE groups` 持有的行锁直到事务提交才释放**，这带来两个后果：

- **好处**：同一个群内的消息分配被串行化，`seq` 严格单调、无并发冲突、无需重试。
- **代价**：`seq` 的分配顺序 == 事务提交顺序。因此**一个回滚的事务会留下永久空洞**（`seq=105` 被分配但事务回滚，`106` 正常提交，105 从此不存在）。

**空洞是必须处理的，客户端不能假设 `seq` 连续。** 处理方式见 4.3 的 `asOfSeq` 机制。如果客户端按"连续"来设计（比如收到 106 时判断"我缺 105，永远等不到"），就会卡死在这个群上——**这是本节最容易踩的坑**。

**② 锁的粒度是群，不是库。** 不同群的消息互不阻塞。单群吞吐上限 ≈ `1000ms / 锁持有时间`。锁持有时间主要是那个事务里的 INSERT 耗时，实测通常 1-3ms（含 outbox 写入），因此单群上限约 **300-1000 条/秒**。50 人团队的实际峰值是每秒几条，**余量三个数量级**。这个估算要写进文档，因为"行锁会不会成瓶颈"是评审时必被问到的问题（结论：不会，且有量化依据）。

**任务编号 `task_no` 用完全相同的模式**（`groups.task_seq`），但它是 `INT` 且不需要参与同步逻辑，所以不要求客户端做任何特殊处理。

### 4.3 离线补投 `sync:pull`（不丢消息的核心）

#### 4.3.1 客户端状态

每个群维护三个东西：

```ts
{
  syncedSeq: number,          // 已连续应用的最高 seq；服务端权威值为准
  pendingNew: MessageDTO[],   // 实时流中因断层而暂存的消息（seq > syncedSeq + 1）
  eventBuffer: EventDTO[]     // 补投进行中收到的实时事件（不得丢弃，见 4.3.4）
}
```

#### 4.3.2 握手与判定

```
连接建立后：
  Client → sync:hello { groups: [{ groupId, syncedSeq }] }
  Server → sync:ready { groups: [{ groupId, lastSeq }] }

客户端对每个 lastSeq > syncedSeq 的群发起补投：
  Client → sync:pull { groupId, sinceSeq: syncedSeq, limit: 200 }
  Server → { items: MessageDTO[], asOfSeq: number, hasMore: boolean }
  Client → 应用 items；把 syncedSeq 推进到 asOfSeq；若 hasMore 则继续拉下一页
```

#### 4.3.3 `asOfSeq` —— 解决"空洞"与"分页"的同一个机制

**服务端返回 `asOfSeq`，而不是让客户端自己算最大值。** 定义：

- 若 `items` 非空：`asOfSeq = items[items.length - 1].seq`
- 若 `items` 为空且 `hasMore = false`：`asOfSeq = 该群当前的 groups.last_seq`

客户端**无条件把 `syncedSeq` 推进到 `asOfSeq`**，即使中间有跳跃（比如返回 `[106, 107]` 而本地是 `104`）。理由：`sync:pull` 的结果就是服务端的权威答案——105 不在结果里，说明它已被回滚，永久不存在。客户端不需要（也无法）区分"被回滚的空洞"和"我没收到"，**只要相信补投结果**。

**这条是整个同步机制的基石。** 如果客户端改成"必须连续才推进"，回滚空洞会让它永久卡住；如果客户端改成"跳跃时自己重试拉 105"，会陷入死循环。

#### 4.3.4 补投进行中的实时事件（竞态处理）

补投是一次网络往返，期间实时流仍在推送。三类事件都可能撞进来：

| 撞进来的事件 | 处理 |
|---|---|
| `message:new`，`seq == syncedSeq + 1` | 直接应用，`syncedSeq++` |
| `message:new`，`seq > syncedSeq + 1` | 说明补投还没到位：塞进 `pendingNew`，不应用 |
| `message:new`，`seq <= syncedSeq` | 重复投递（弱网重发/重连重叠），**按 `id` 去重后丢弃** |
| `message:updated` / `message:deleted` | **一律塞进 `eventBuffer`，绝不丢弃** |

补投完成后（`hasMore = false`）：按 `seq` 升序排空 `pendingNew`，再按到达顺序排空 `eventBuffer`。应用事件时用 `updatedAt` 比较：**只有事件的 `updatedAt` 大于本地已存该消息的 `updatedAt` 才覆盖**，否则忽略。

由此推出一条**接口契约上的硬要求**：

> **`message:updated` 与 `message:deleted` 事件必须携带完整消息 DTO（而不是 diff），且 DTO 必须包含 `updatedAt`。**
>
> 理由：携带完整 DTO 让事件的应用变成幂等操作（重复应用结果相同）；配合 `updatedAt` 比较，事件的乱序到达也不会产生错误状态。如果事件只带 diff（例如"body 改为 X"），就必须严格按顺序应用，而实时流在重连场景下无法保证顺序——这会把一个简单问题变成一个必须做序列号排序的复杂问题。

#### 4.3.5 编辑与撤回为什么不需要"事件重放"

**这是本方案与常见自研聊天实现差异最大的一点，也是最容易被漏的一点。**

补投的输入参数只有 `sinceSeq`。而**编辑与撤回事件本身没有 `seq`**（它们不改变消息在群内的位置）。如果实现成"补投时重放事件流"，就必须回答一连串难题：编辑事件该挂哪个 seq？重放的顺序如何保证？重放到一半又收到实时事件怎么办？

**正确做法：补投直接返回消息的当前状态，不重放事件。**

`messages` 表的行是**原地更新**的（编辑覆盖 `body`、撤回置 `deleted_at`），所以一次 `SELECT` 天然返回最新状态。补投把 `{ seq: 100, body: '改后的内容', edited_at: '...' }` 一次性交给客户端，客户端 `upsert` 到位即可。

**反例（说明为什么必须这样）**：我离线期间，有人发了 `seq=100` 又撤回了它，接着又编辑了 `seq=98`。
- 若用事件重放：客户端会收到 `发送(100)`、`撤回(100)`、`编辑(98)` 三个事件，需要按时间排序，且如果"撤回(100)"先于"发送(100)"到达（网络乱序或分批拉取），会找不到目标消息而丢弃撤回 → **客户端永久显示一条本该消失的消息**。
- 用当前状态：客户端一次拿到 `{100, deleted_at}` 与 `{98, body:'新内容'}`，天然正确。

#### 4.3.6 客户端如何发起补投（两个路径）

| 路径 | 用途 | 说明 |
|---|---|---|
| **WS 事件 `sync:pull`**（主路径） | 通过 Socket.IO 的 ack 机制做请求-响应 | 与实时流在同一条连接上，天然共享鉴权与在线状态 |
| **HTTP `GET /api/v1/groups/:gid/sync?sinceSeq=`**（兜底） | WS 不可用（公司网络屏蔽 WebSocket、代理不支持 Upgrade）时的降级 | 前端在 WS 连续重连失败 N 次后切换到 HTTP 轮询补投，保证"至少能看到消息" |

两条路径**必须调用同一个 service 函数**，不允许各写一份查询——否则两个路径的行为会漂移，而这类漂移几乎不可能被测出来。

### 4.4 已读位点与已读回执

#### 4.4.1 位点推进（必须单调）

```sql
INSERT INTO read_positions (user_id, group_id, last_read_seq, mentions_read_seq, updated_at)
VALUES ($1, $2, $3, $4, now())
ON CONFLICT (user_id, group_id) DO UPDATE
   SET last_read_seq     = GREATEST(read_positions.last_read_seq, EXCLUDED.last_read_seq),
       mentions_read_seq = GREATEST(read_positions.mentions_read_seq, EXCLUDED.mentions_read_seq),
       updated_at        = now();
```

**`GREATEST` 是必须的**：同一个账号可能桌面端与浏览器端同时在线，桌面端已经读到 `seq=500`，手机端（网络延迟、或用户翻旧消息时上报了小值）再上报 `seq=480`。若无条件覆盖，位点会倒退，未读数会突然暴涨——用户会认为"这软件把我消息弄丢了"。同理，`mentions_read_seq` 独立于 `last_read_seq`，因为"@我的"未读与"群消息"未读是两套独立的消费进度。

#### 4.4.2 未读数计算（必须限界）

**不能**写成 `SELECT groups.last_seq - read_positions.last_read_seq`：这个差值包含了自己发的消息与系统消息，会显示假的未读数。

**也不能**写成不设界的 `SELECT count(*)`：一个用户放假两周回来，某群可能有 5000 条未读，`count(*)` 要扫 5000 行，而列表页有 8 个群——一次打开客户端就要扫几万行。

**正确做法：限界计数 + 99+ 封顶**（客户端只需要知道"很多"，不需要精确值）：

```sql
SELECT count(*) FROM (
  SELECT 1
    FROM messages m
   WHERE m.group_id = $1
     AND m.seq > $2                    -- 我的 last_read_seq
     AND m.sender_id IS DISTINCT FROM $3   -- 排除自己发的
     AND m.kind <> 'system'                -- 排除系统消息
   LIMIT 100
) t;
```

`LIMIT 100` 让最坏情况固定为扫 100 行。客户端拿到 100 时显示 `99+`。

#### 4.4.3 已读回执名单（开放展示，但要分级）

技术上，位点即回执：**某人的 `last_read_seq >= 该消息的 seq`，就说明他读到了这条。**

```sql
-- 聚合（便宜，走 index read_positions(group_id, last_read_seq)）
SELECT count(*) AS read_count
  FROM read_positions rp
  JOIN group_members gm
    ON gm.group_id = rp.group_id AND gm.user_id = rp.user_id AND gm.removed_at IS NULL
 WHERE rp.group_id = $1
   AND rp.last_read_seq >= $2
   AND rp.user_id <> $3;              -- 排除发送者自己
```

| 展示层级 | 触发 | 代价 |
|---|---|---|
| **聚合**（"已读 8/25"） | 消息列表滚动到可见区即请求，结果**进客户端缓存**（位点单调，结果只会变大，可用 `updatedAt` 做短 TTL 缓存） | 一次索引 count，便宜 |
| **名单**（具体谁读了） | 仅当用户**点击**展开，且**仅对 `task_card` / 命中 @我 / 公告类消息默认展开** | 多一次 JOIN users；群上限 50 人，一次最多 50 行，可接受 |

**为什么普通消息默认只给聚合**：25 人群里每条消息都渲染"已读 8/25 + 名单"，界面会被噪音淹没；而且会改变团队行为（有人开始盯着谁没读）。分级展示是技术上的折中，**使用规范属于产品决策，不写在后端册，但后端要把"聚合"与"名单"拆成两个接口/参数**，让前端有能力做这个分级。

#### 4.4.4 已读回执的两个已知边界

1. **位点会"追认"**：A 读了 `seq=100`，就意味着 A 也读了 1..100。所以对 `seq=50` 的消息，A 永远显示已读——**即使 A 其实是直接跳到最新消息、根本没翻到 50**。这是位点模型的固有语义，不是 bug。要在前端文案上避免"已读"这个强断言，改用"已读到此"或"已读到第 N 条"。
2. **离线用户位点陈旧**：正确的。用户下次上线读完后位点才推进，回执随之更新。

### 4.5 任务状态机

#### 4.5.1 状态与允许的流转

```
                  ┌──────────────────────────────────────┐
                  │                                      │
  publish         │        reject(必填原因)               │
     │            ▼              │                       │
     ▼        ┌────────┐         │                       │
 ┌────────┐   │in_prog │─────────┘                       │
 │pending │   │ ress   │                                 │
 └───┬────┘   └────┬───┘                                 │
     │ accept      │ submit                              │
     ▼             ▼                                     │
 ┌────────┐   ┌──────────┐   approve                    │
 │accepted│   │submitted │───────────► ┌──────┐          │
 └───┬────┘   └──────────┘             │ done │          │
     │ start                           └──────┘          │
     └──────────► in_progress                             │
                                                          │
  cancel（owner/admin，任意非终态）─────────────────────────► cancelled
```

| 从 | 到 | 触发者 | 附加校验 |
|---|---|---|---|
| — | `pending` | owner/admin（发布） | 负责人必须是本群有效成员 |
| `pending` | `accepted` | 负责人 | 只能接取指派给自己的任务 |
| `accepted` | `in_progress` | 负责人 | — |
| `accepted` / `in_progress` | `submitted` | 负责人 | 创建 `task_acceptances` 轮次记录（`round_no` 递增） |
| `submitted` | `done` | **owner/admin 且非本次提交者** | 回填该轮 `task_acceptances.result='approved'` |
| `submitted` | `in_progress` | **owner/admin 且非本次提交者** | **打回原因必填**；回填 `result='rejected'`；`round_no` 已递增，下轮重新提交 |
| 任意非终态 | `cancelled` | owner/admin | — |
| `done` / `cancelled` | — | — | **终态，不可再流转** |

**注意 `accepted → submitted` 是允许的**：不强制必须先点"开始"。强制"开始"只是为了让管理者看到信号，但会给工作者增加一次无意义的点击，实际结果是大家忘了点导致状态失真——**不如允许直接提交**。

#### 4.5.2 原子流转（防并发与防重复）

所有流转都用同一个模式，**这是防止"两人同时接取同一任务"与"验收被重复提交"的唯一可靠手段**：

```sql
UPDATE tasks
   SET status       = $to,
       updated_at   = now(),
       -- 各终态/中间态的时间戳在同一语句里按目标状态赋值，避免多次 UPDATE
       accepted_at  = CASE WHEN $to = 'accepted'  THEN now() ELSE accepted_at  END,
       submitted_at = CASE WHEN $to = 'submitted' THEN now() ELSE submitted_at END,
       done_at      = CASE WHEN $to = 'done'      THEN now() ELSE done_at      END,
       cancelled_at = CASE WHEN $to = 'cancelled' THEN now() ELSE cancelled_at END
 WHERE id = $id
   AND status = ANY($allowed_from)      -- 允许的来源状态
RETURNING id;
```

- **返回 0 行** → 说明当前状态不在允许集合内（并发下已被别人改走，或非法流转）→ 返回 `409 STATE_MACHINE_VIOLATION`，响应体带上**当前实际状态**，前端据此刷新而不是弹通用错误。
- 这一步与后续的 `INSERT task_status_history`、`UPDATE task_acceptances` 必须在**同一个事务**里，否则会出现"状态变了但历史没记"，而统计模块完全依赖历史表。

**不要用 `SELECT` 查状态再 `UPDATE`**（check-then-act）：两个请求可能都读到 `submitted` 然后都执行验收，产生两条验收记录。这个 bug 在压力测试里很难复现，但在"两个人同时看到任务并都去点验收"时会真实发生。

#### 4.5.3 状态历史与打回次数

`task_status_history` 每次流转插一行，含 `from_status` / `to_status` / `actor_id` / `reason`。打回次数由历史派生：

```sql
SELECT count(*) AS reject_count
  FROM task_status_history
 WHERE task_id = $1
   AND from_status = 'submitted'
   AND to_status   = 'in_progress';
```

`round_no` 记录在 `task_acceptances`，与上面的计数应当一致——**建议加一个校验任务**（见 9.2 的对账项），两者不一致说明状态机与历史表出现了写入不一致。

### 4.6 在线状态与死连接清理

在线状态**只放进程内存**（`Map<userId, Set<socketId>>`），不落库。理由是单进程部署下内存天然是权威，落库只会引入一致性负担。

| 机制 | 配置 | 说明 |
|---|---|---|
| 心跳 | Socket.IO `pingInterval: 10000`、`pingTimeout: 15000` | 15 秒内没收到 pong 就判定连接死亡并触发 `disconnect` |
| 多端 | 一个用户可有多个 socketId（桌面 + 浏览器） | 只有集合变空才广播 `presence:offline` |
| 清理 | 在 `disconnect` 事件里 **同步** 从集合中移除 | 移除必须是同步的第一行代码——如果放在 `await` 之后，连接会在断开期间仍被算作在线，并在广播时尝试向死连接发消息 |
| 兜底扫描 | 每 30 秒对比 `io.engine.clientsCount` 与 presence 集合总数，差值 > 20 时告警 | 这是检测"presence 泄漏"的探针；泄漏会导致内存缓慢增长直至 OOM，是本系统特有的高频故障（见 `03-AI运维手册.md` 故障剧本 5） |

**为什么必须有兜底扫描**：`disconnect` 在某些网络场景下（NAT 超时、客户端休眠后 TCP 半开、进程被强杀）不一定触发。只依赖事件回调就等于把内存正确性押在网络行为上。

### 4.7 必须暴露的内部指标

`GET /internal/metrics`（仅内网可访问，由巡检脚本与 agent 拉取）输出以下字段。**这些指标不是"有了更好"，而是 `03-AI运维手册.md` 里若干巡检项与自愈剧本的输入**，缺一项就等于那条巡检失效：

| 指标 | 类型 | 被谁消费 |
|---|---|---|

| `outboxPending` | gauge | 巡检项「outbox 积压」 |

### 5.9 WebSocket 事件表

握手鉴权：连接时在 `auth.token` 里带 access token；校验失败立即断开并回 `connect_error`，客户端据此触发刷新后重连。

**Client → Server**（除 `typing:*` 外都有 ack 回调）

| 事件 | 载荷 | ack | 说明 |
|---|---|---|---|
| `sync:hello` | `{groups: [{groupId, syncedSeq}]}` | `{groups: [{groupId, lastSeq}], contractVersion}` | 连接后第一件事；不传则收不到增量 |
| `sync:pull` | `{groupId, sinceSeq, limit}` | `{items, asOfSeq, hasMore}` | 补投主路径 |

| `typing:start` / `typing:stop` | `{groupId}` | 无 ack | **尽力而为，可丢**；不落库 |

**Server → Client**

| 事件 | 载荷 | 触发时机 |
|---|---|---|
| `sync:ready` | `{groups: [{groupId, lastSeq}], contractVersion}` | `sync:hello` 之后 |

| `read:updated` | `{groupId, userId, lastReadSeq}` | 有人推进位点 → 已读回执实时刷新 |
| `presence:updated` | `{groupId, userId, online, at}` | 上下线 |
| `mention:new` | `{messageId, groupId, fromUserId}` | 触发桌面通知与红点 |

## 6. 数据库设计

> 本节的 DDL 是**全系统唯一真源**。其他三册（尤其 AI 运维手册里的 `ops_runs` / `audit_logs` / `ops_requests` 与恢复演练的验收 SQL）都以本节为准。修改任何表必须同时更新本节，并且遵循 6.11 的迁移规范。

### 6.1 设计原则与表清单

**三条贯穿性设计原则**：

1. **`group_id` 是几乎所有业务表的分区键**。因为「群即项目容器」——任务、消息、评论、文件全部挂在群下。这让权限校验可以统一成「你是不是这个群的成员」，而不需要每张表写一套规则。
2. **所有删除都是软删除**（`deleted_at` / `removed_at` / `revoked_at` / `disabled_at`）。工作系统的记录需要留痕，且硬删除会破坏群聊上下文、任务历史与审计。物理删除只发生在附件清理（且有严格条件）。
3. **多态外键一律拆成独立表**，不用 `owner_type + owner_id`。代价是表数量多一点（`message_attachments` 与 `task_comment_attachments` 两套），收益是外键约束真实生效——多态外键无法建 FK，会积累悬挂引用。

**22 张表**（分组）：

| 组 | 表 | 说明 |
|---|---|---|
| 账号 | `users`、`sessions`、`notification_prefs` | |
| 群 | `groups`、`group_members`、`group_invites` | `groups.last_seq` / `task_seq` 是两个分配器 |
| 消息 | `messages`、`message_attachments`、`message_mentions`、`message_refs`、`read_positions` | 系统复杂度主要在这里 |
| 任务 | `tasks`、`task_status_history`、`task_acceptances`、`task_comments`、`task_comment_attachments` | |
| 文件 | `files` | 与两套 attachments 表配合 |
| 搜索 | `outbox` | transactional outbox |
| 审计与运维 | `audit_logs`、`ops_requests`、`ops_runs`、`ops_heartbeat` | 供 AI 运维手册消费 |

### 6.2 扩展与枚举

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;    -- 搜索降级路径（中文 2 字以上可用）
CREATE EXTENSION IF NOT EXISTS pgcrypto;   -- gen_random_uuid()

CREATE TYPE group_role      AS ENUM ('owner', 'admin', 'member');
CREATE TYPE message_kind    AS ENUM ('text', 'image', 'file', 'system', 'task_card');
CREATE TYPE task_status     AS ENUM ('pending', 'accepted', 'in_progress', 'submitted', 'done', 'cancelled');
CREATE TYPE task_priority   AS ENUM ('low', 'normal', 'high', 'urgent');
CREATE TYPE comment_kind    AS ENUM ('comment', 'system');
CREATE TYPE review_result   AS ENUM ('approved', 'rejected');
CREATE TYPE file_storage    AS ENUM ('local', 'oss');
CREATE TYPE file_status     AS ENUM ('pending', 'ready', 'cleaned');
CREATE TYPE ops_severity    AS ENUM ('info', 'warning', 'critical');
CREATE TYPE ops_trigger     AS ENUM ('timer', 'threshold', 'manual');
CREATE TYPE ops_req_status  AS ENUM ('pending', 'approved', 'rejected', 'running', 'done', 'failed', 'expired');
```

**为什么用原生 ENUM 而不是 `VARCHAR + CHECK`**：ENUM 占用 1 字节、比较快、`psql` 里可读性好。代价是**加值需要 `ALTER TYPE ... ADD VALUE`，且该语句在 PG 中不能与后续使用同值的事务在同一事务里提交**。因此新增枚举值必须单独一条迁移、单独提交，不能在加值的同时修改代码路径。这条限制写在这里避免踩坑——如果未来枚举值变更频繁（比如状态要加很多），改用 `VARCHAR + CHECK` 更灵活。

> ⚠️ **本代码块必须最先执行。** 它是 `0001_init.sql` 的头部。6.5 节的 DDL 引用了这里定义的扩展与枚举类型，**单独复制 6.5 会直接报 `type "group_role" does not exist`**。合并后的完整文件见 6.5 节开头的说明。

### 6.3 任务卡片复用消息表的理由

任务卡片（"张三发布了任务 #12：修复登录问题"）作为消息出现在群聊里，实现上**复用 `messages` 表**（用 `kind='task_card'` + `task_id` 外键 + `meta` JSONB 存卡片渲染字段），而不是新建一张「任务动态表」。

**否决独立通道的理由**：

| 如果独立通道 | 后果 |
|---|---|
| 前端要维护两个流 | 群聊流 + 任务动态流，要按时间合并成一条时间线，而两个流的顺序无法保证一致（一个走 `seq`，一个走时间戳） |
| 未读要算两遍 | 未读数、@我、已读回执都要在两套数据上各实现一次 |
| 搜索要索引两遍 | 用户搜"登录问题"既是消息也可能是任务动态，分两处搜体验割裂 |
| 撤回语义分叉 | 消息能撤回、任务动态不能？还是都能？规则会变得无法解释 |

**代价**：`messages` 表多一个可空 `task_id` 外键 + `meta` JSONB。这是很小的代价，换来"一个实体只有一个写入口"的清晰性。

**卡片必须带 `meta` 快照**（任务标题、负责人显示名、优先级、截止时间），不能只存 `task_id` 让前端回查。理由：① 群聊历史是**快照语义**——"当时这句话长什么样"不应随任务被改名而变；② 拉一屏消息不用 JOIN 任务表，避免 N+1；③ 任务被删除时卡片仍可渲染。前端点击卡片用 `task_id` 跳转，但渲染用 `meta`。

### 6.4 任务评论不镜像到群消息流的理由

需求上「评论不刷群」，实现上就不要"写两份、只展示一份"——**评论只写 `task_comments`，不写 `messages`**。

理由：如果是"写入两份 + 前端只在右侧展示"，那么群消息就变成了 `messages` 里存在但 UI 不显示的消息。这会立刻污染四个地方：未读计数（用户会看到有未读但群里什么都没有）、搜索（搜到一条点进去不在群里）、已读位点（`last_read_seq` 会跳过一条"看不见"的消息，语义混乱）、以及补投（客户端拿到一条不该显示的消息）。

**规则写死：`messages` 表里的每一行都必须是一条能在群聊里显示的消息。** 任何"逻辑上存在但不显示"的消息都不允许写入 `messages`。

代价是任务评论需要自己的附件表与自己的 @提及处理（见 6.6）。

```sql
CREATE TABLE users (

CREATE TABLE messages (
```

### 6.6 @提及在群消息与任务评论中的差异（一处刻意的取舍）

两处的 @ 提及实现不同，这是**刻意的**，要写清楚避免被当成疏漏：

| | 群消息 | 任务评论 |
|---|---|---|
| 存储 | `message_mentions` 表（含 `group_id` + `seq`） | `task_comments.mentioned_user_ids` 数组 |
| 能算未读吗 | **能**。`seq > read_positions.mentions_read_seq` 即"@我未读" | **不能**（刻意的） |
| 提供的能力 | 红点 + 未读列表 + 桌面通知 | 实时桌面通知 + 任务详情里高亮姓名 |

**为什么任务评论不做未读**：任务评论不在消息流里，**没有 `seq`**，因此没有天然的位点可以推进。要做未读就必须引入第二套水位线（按任务维度或按群维度的评论水位），而它的收益很小——任务评论的量级是"每个任务下几条到几十条"，且用户本来就会打开任务看。**引入第二套水位线会增加一个跨表一致性问题，不值得。**

**如实说明的局限**：用户可能错过任务评论里的 @（因为只发一次实时通知，没看到就没了后续提醒）。缓解方式是前端在任务卡片上显示"有新评论"（基于 `tasks.comment_count` 与本地记录的比较，纯客户端逻辑，不落库）。**如果将来这个局限被真实抱怨，再补未读水位**——这是有意留的扩展点，不是设计缺陷。

### 6.7 跨群「我的任务」查询

`GET /me/tasks` 是这个系统里被低估的关键接口。一个用户可能同时在 6 个群里，如果只能按群看任务，他每天要切 6 次才能知道自己该干什么。查询：

```sql
SELECT t.*
  FROM tasks t
  JOIN group_members gm
    ON gm.group_id = t.group_id AND gm.user_id = $1 AND gm.removed_at IS NULL
 WHERE t.assignee_id = $1
   AND ($2::task_status IS NULL OR t.status = $2)
   AND ($3::boolean IS NOT TRUE OR (t.due_at < now() AND t.status NOT IN ('done','cancelled')))
   AND (:cursor_due, :cursor_id) < (t.due_at, t.id)   -- 游标分页
 ORDER BY t.due_at ASC NULLS LAST, t.id DESC
 LIMIT 50;
```

走索引 `tasks_by_assignee`。注意 `JOIN group_members` 是必要的——**防止用户被移出群后仍能看到该群的任务**。这个 JOIN 在 `assignee_id` 已大幅收窄结果集后成本很低。

### 6.8 统计查询与隐私分级

**不新建统计表、不建物化视图**，全部从 `tasks` / `task_acceptances` / `task_status_history` 实时算。理由：数据量小（群内任务数百到数千），且物化视图需要刷新调度与失效处理，是纯增加的复杂度。

```sql
-- 本周团队交付与平均交付周期（团队汇总，成员可见）
SELECT
  count(*)                                              AS delivered,
  avg(ta.reviewed_at - t.created_at)                    AS avg_cycle,
  count(*) FILTER (WHERE ta.reviewed_at = ta.submitted_at
                     OR (ta.reviewed_at - ta.submitted_at) < interval '1 day') AS fast_delivered
  FROM tasks t
  JOIN task_acceptances ta ON ta.task_id = t.id AND ta.result = 'approved'
 WHERE t.group_id = $1
   AND ta.reviewed_at >= $2 AND ta.reviewed_at < $2 + interval '7 days';

-- 逾期清单
SELECT id, task_no, title, assignee_id, due_at
  FROM tasks
 WHERE group_id = $1 AND status NOT IN ('done','cancelled') AND due_at < now()
 ORDER BY due_at;

-- 卡住最久的任务：当前状态持续时长
SELECT t.id, t.task_no, t.title, t.status,
       now() - COALESCE(max(h.created_at), t.created_at) AS stuck_for
  FROM tasks t
  LEFT JOIN task_status_history h ON h.task_id = t.id
 WHERE t.group_id = $1 AND t.status NOT IN ('done','cancelled')
 GROUP BY t.id
 ORDER BY stuck_for DESC
 LIMIT 10;
```

**隐私分级（这是刻意的设计约束，不是可选项）**：

| 数据 | 谁能看 | 实现 |
|---|---|---|
| 团队汇总（交付数、平均周期、逾期清单、打回总数、卡住最久的任务是哪个） | **所有群成员** | `GET /groups/:gid/stats/weekly`，只走 `GroupMemberGuard`（不给负责人姓名以外的个人聚合） |
| 个人维度（每人交付数、每人平均周期、每人被打回次数） | **owner / admin** | `GET /groups/:gid/stats/members`，额外加 `GroupRoleGuard(['owner','admin'])` |

**为什么个人数据只给管理者**：这套统计能精确算出每个人的产出，一旦对全员公开个人排名，会直接催生刷任务数的行为（把一件事拆成十件），也会让成员感到被考核。团队汇总（"我们这周交付了 23 件，有 3 件逾期"）已经足够起到推进作用，而它不会指向具体某个人。

**这条是产品决策，后端要做的只是把它拆成两个接口**。如果后续决定公开个人数据，改的是前端展示与接口权限，不涉及数据结构。**需要注意的矛盾**：群内自动周报只发团队汇总；如果管理员把个人维度截图发到群里，那是人的行为，系统无法也不应阻止——但使用规范里应当写明。

### 6.9 搜索：outbox + Meilisearch + 降级

**三段结构**：

```
写业务数据（同事务）──► outbox 表 ──► worker 消费 ──► Meilisearch 索引
                                        │
                                        └─ 失败：attempts++，last_error 记录，下轮重试（幂等 upsert）

查询：Meilisearch 命中 ──► 返回（degraded=false）
      Meilisearch 不可用 ──► pg_trgm LIKE 查询 ──► 返回（degraded=true）
```

**为什么 outbox 里的 `payload` 必须自包含**：worker 消费时**不回查 `messages` 表**。若回查，会在"写入 outbox 之后、worker 消费之前消息被编辑"时把**旧内容**写进索引（因为 worker 读到的是回查时的新内容还是旧内容取决于时序）。更糟的是"消息改了又改"，worker 可能把中间态写进索引并在之后不再修正。自包含 payload 让每次索引写入都是**当时那个版本的状态**，配合 outbox 的追加顺序，最终一致。

**幂等**：Meilisearch 用文档主键 upsert（主键 = `message:id` / `comment:id`），重复消费同一 outbox 行结果相同。因此 worker 的提交语义是"处理成功即置 `processed_at`"，失败不置位，靠重试。

**outbox 的清理**：已处理的记录保留 7 天后删除（不是立即删，便于排查"为什么这条没进索引"）。

**降级查询**：

```sql
SELECT id, group_id, seq, sender_id, left(body, 200) AS snippet, created_at
  FROM messages
 WHERE group_id = $1
   AND deleted_at IS NULL
   AND body ILIKE '%' || $2 || '%'
 ORDER BY seq DESC
 LIMIT 30;
```

走 `messages_body_trgm` GIN 索引。**中文场景的已知局限**：`pg_trgm` 对**单字查询**几乎无效（三元组无法构成），对 2 字以上可用但排序质量不如 Meilisearch。这个局限要如实写在文档里——降级状态下"搜索质量下降"是真的下降，而不是"无缝切换"。

**索引范围**：只索引 `messages` 与 `task_comments` 的正文（`deleted_at IS NULL` 且 `kind IN ('text','task_card')`）。不索引附件内容、不索引被撤回的消息。撤回时向 outbox 写一条 `event_type='delete'`，worker 从索引里删掉。

### 6.10 容量估算与「M1 不分区」的结论

按 50 人、每群日均 60 条消息、平均 12 个活跃群估算：

| 对象 | 单条大小（含行开销） | 日增量 | 年增量 |
|---|---|---|---|
| `messages` 行 | 正文 150B + 行/索引开销约 250B ≈ **400B** | 60 × 12 = 720 条 ≈ 290KB | ≈ **100MB** |
| `messages` 索引（3 个） | ≈ 行大小的 1.2 倍 | ≈ 350KB | ≈ 125MB |
| `messages_body_trgm` GIN | 中文三元组膨胀，约为正文的 3-5 倍 | ≈ 650KB | ≈ **230MB** |
| `message_mentions` | ≈ 80B | 视 @ 频率，取 10% | ≈ 10MB |
| `task_comments` + 历史 + 验收 | —— | —— | ≈ 20MB |
| `audit_logs` | ≈ 300B | 数百条 | ≈ 40MB |
| `outbox`（保留 7 天） | 稳态滞留量 | —— | 可忽略 |
| **PG 合计** | | | **≈ 550MB/年** |
| 附件（磁盘，不在 PG） | 单文件均值 800KB，50 人 × 8 个/天 | **≈ 320MB/天 ≈ 9.6GB/月** | **≈ 115GB/年** |

**结论：消息表 5 年内约 500 万行、PG 约 3GB，完全不需要分区。** 分区裁剪的收益要到千万行级才明显，而分区会带来两个实际代价：

1. **分区会破坏幂等去重的唯一索引。** PostgreSQL 要求分区表的唯一索引必须包含分区键。若按时间分区，`(sender_id, client_msg_id)` 就必须变成 `(sender_id, client_msg_id, created_at)`——**而这三列组合并不能保证全局唯一**（同一 clientMsgId 落到不同分区就是两行），幂等机制直接失效。这是否决分区的**决定性理由**，不是性能考量。
2. 查询必须带上分区键，而"拉某群最近 50 条"这类查询没有时间条件（用户可能翻到很久以前），导致跨分区扫描。

**触发分区的条件（提前写清，避免将来争论）**：当 `messages` 超过 **3000 万行**（约 40 年数据量，或该表被用于远超预期的场景）时再评估。届时更可能的正确做法是**归档到冷存表**（`messages_archive`）而不是分区。

**真正需要盯的是附件**：按上表，**100G 磁盘约 10 个月**（含系统与其他占用，实际留 20% 余量约 8 个月）。因此：

- 单文件上限 **50MB**、单用户配额 **2GB**、图片强制压到最长边 1600px / quality 78
- 附件清理任务在磁盘用量超阈值时触发（见 `03-AI运维手册.md` 巡检项）
- `files.storage` 字段已预留 `oss`，切对象存储只需加一个 driver

### 6.11 迁移规范：扩展-收缩两阶段

**硬规则：破坏性变更（DROP COLUMN、改类型、加 NOT NULL、重命名）不允许与代码发布在同一个版本。**

```
版本 N     ：加新列（可空）/ 加新表 / 加新索引 CONCURRENTLY
版本 N+1   ：代码切换到读写新列（双写或回填）
版本 N+2   ：删除旧列（在确认 N+1 已全量部署且无回滚需求后）
```

**理由**：**镜像只前进、不回退数据库**。回滚时旧镜像要跑在当前 schema 上，所以任何时刻的 schema 都必须与"上一版代码 + 当前版代码"都兼容。如果破坏性变更与代码同版本发布，那么一旦需要回滚，旧代码面对已经删掉列的数据库会直接崩——**零停机部署与回滚能力同时失效**。

**配套要求**：

| 项 | 要求 |
|---|---|
| 迁移文件 | 顺序编号 `0001_init.sql`、`0002_xxx.sql`…，**只增不改**。已发布的迁移文件禁止编辑（否则不同环境的 schema 会分叉） |
| 迁移执行 | `migrate.ts` 先取咨询锁（`pg_advisory_lock`），再逐条执行未应用的迁移，记录在 `schema_migrations` 表。**幂等**，可重复运行 |
| 加索引 | 大表加索引必须用 `CREATE INDEX CONCURRENTLY`（不能包在事务里，所以迁移执行器要支持非事务型迁移） |
| 数据回填 | 大表回填必须分批（`LIMIT` + 循环），且单独一个迁移，不与加列混在一起 |
| 回滚 | **不写 down 迁移**。回滚靠"部署上一个镜像"，schema 由扩展-收缩规则保证兼容 |

### 6.12 软删除与附件清理的一致性

**软删除的三处语义**：

| 对象 | 标记 | 效果 |
|---|---|---|
| 消息撤回 | `messages.deleted_at` + `deleted_by` | 群聊里显示"该消息已撤回"；`/messages/:mid/raw` 可查原文（owner/admin）；搜索索引删除该文档 |
| 任务评论删除 | `task_comments.deleted_at` | 任务详情里显示已删除占位 |
| 成员移除 | `group_members.removed_at` | 不再能看到该群内容；历史消息里的显示名仍可查（不置 NULL） |

**附件清理的准确条件**（这是 6.9 之外的另一个易错点）：

`files.ref_count` **不能作为清理依据**——因为软删除的消息仍持有 attachments 行，`ref_count` 不会归零，附件将永远无法清理。清理必须直接判断"是否还有**未被软删除的**引用"：

```sql
-- 清理候选（分批，每批 500）
SELECT f.id, f.object_key, f.byte_size
  FROM files f
 WHERE f.status = 'ready'
   AND f.created_at < now() - interval '180 days'
   AND NOT EXISTS (
     SELECT 1 FROM message_attachments ma
       JOIN messages m ON m.id = ma.message_id
      WHERE ma.file_id = f.id AND m.deleted_at IS NULL)
   AND NOT EXISTS (
     SELECT 1 FROM task_comment_attachments tca
       JOIN task_comments tc ON tc.id = tca.task_comment_id
      WHERE tca.file_id = f.id AND tc.deleted_at IS NULL)
 ORDER BY f.created_at
 LIMIT 500;
```

清理流程（顺序不能变，否则会产生悬挂引用）：

```
1. 选出候选（上面的 SQL）
2. 逐个把 files.status 置 'cleaned'（先置状态，再删文件）
3. 从磁盘/对象存储删除对象
4. 保留 files 行（不物理删除记录），把 object_key 清空
```

**为什么"先置状态再删文件"**：如果先删文件、后置状态，进程在中间崩溃会留下 `status='ready'` 但对象已不存在的记录，前端请求下载会 404 且系统不知道原因。反过来崩溃则留下"状态说已清理但文件还在"——这只是浪费空间，不影响正确性。**任何清理流程都要选"崩溃后偏保守"的顺序。**

**与「文字永久保留」的张力**：文字永久保留 + 附件可清理 = **历史记录不完整**。这在方案评审时被明确标出过：如果公司有记录保留义务（合同、报价、对账单），这类文件不应通过本系统的附件通道传递。这一条要在使用说明里写明，而不是靠系统约束。

## 7. 契约治理（两人分工下接口不一致的唯一防线）

**问题**：两个人分别写前端和后端，最频繁的阻塞不是技术难题，而是"我按 A 字段名调，你返回的是 B"。而且这类问题往往在联调当天才暴露，一次就要卡半天。

**唯一数据源：`packages/contracts`。**

```
packages/contracts/src/
├── http/
│   ├── auth.ts        export const LoginReq = z.object({...});
```

**四道防线**：

| # | 防线 | 实现 | 拦住什么 |
|---|---|---|---|
| 1 | **运行时双向校验** | 后端入参走 Zod 校验管道；**出参也校验**（dev 严格模式抛错，生产记录不一致日志并告警）。前端对每个响应做 `schema.parse`，失败则提示"数据格式异常"并上报 | 后端偷偷返回了未声明的字段、或漏了字段；前端拿到结构不对的数据继续渲染导致难以定位的白屏 |
| 2 | **编译期类型** | 前端 `import type { TaskDTO } from '@app/contracts'`；WS 客户端 `socket.on<ServerToClientEvents>` 全类型化 | 字段改名、枚举加值后前端忘了改（编译直接报错，而不是运行时 undefined） |
| 3 | **OpenAPI 快照 + CI** | CI 步骤：`pnpm contracts:openapi` 生成 `openapi.json`，然后 `git diff --exit-code`。不一致则 CI 红 | 接口改了但没提交契约变更，等于单方面改了协议 |
| 4 | **CONTRACT_VERSION 版本守卫** | 服务端启动时计算 contracts 包的 hash 前 8 位作为 `CONTRACT_VERSION`，在 `sync:hello` / `sync:ready` 里下发。客户端比对不一致则弹"客户端版本过旧，建议升级"，但**不拒绝服务** | 桌面客户端长期不升级导致 WS 事件语义漂移（比如服务端改了 `task:changed` 的字段，老客户端渲染出错） |

**第 4 条为什么不拒绝服务**：内部办公系统里，因为版本不一致就把用户挡在门外，比让他看到一个字段缺失更糟。正确做法是提醒 + 记录版本分布（谁在用老版本），由管理员在群里催升级。

**流程约束（写进 team README，不是建议而是规则）**：

1. **任何涉及接口的改动，PR 必须同时修改 `packages/contracts`。** 只改一端的 PR 不许合并。这条是四道防线能生效的前提——如果契约可以被绕过，防线就只是装饰。
2. **联调期每天固定 10 分钟同步一次 contracts 的 diff**，比事后排查便宜得多。
3. `apiRoutes` 映射表是**唯一**允许硬编码路径的地方；业务代码里不许出现字符串形式的路径常量，一律 `apiRoutes.login.path` 这样引用。

## 8. 错误码、限流与文件安全

### 8.1 错误码表

响应格式固定为 `{ error: { code, message, details?, requestId } }`。`code` 是**给程序看的**，`message` 是英文短句**给日志看的**；面向用户的中文文案由前端按 `code` 映射（后端不承担 i18n）。

| HTTP | code | 触发场景 | 前端应有的行为 |
|---|---|---|---|
| 400 | `INVALID_ARGUMENT` | Zod 校验失败，`details` 里是字段级错误 | 表单内联报错 |
| 401 | `UNAUTHENTICATED` | 没有或格式错误的 access token | 触发刷新 |
| 401 | `TOKEN_EXPIRED` | access token 过期 | 静默刷新后重放原请求 |
| 401 | `REFRESH_INVALID` | refresh 不存在/已撤销/过期 | 跳登录页 |
| 401 | `REFRESH_REUSED` | **检测到 refresh 重用，整个 family 已作废** | 跳登录页 + 提示"为安全起见需要重新登录" |
| 403 | `FORBIDDEN_NOT_MEMBER` | 不是该群成员 | 从群列表移除该群，提示"你已不在该群" |
| 403 | `FORBIDDEN_ROLE` | 是成员但角色不够 | 隐藏对应按钮（正常不应触发，说明前端权限渲染错了） |
| 403 | `ACCOUNT_DISABLED` | 账号被禁用 | 跳登录页 + 提示联系管理员 |
| 403 | `CANNOT_REVIEW_OWN_SUBMISSION` | 提交者试图验收自己的任务 | 提示"不能验收自己提交的任务" |
| 404 | `NOT_FOUND` | 资源不存在或不可见 | 从本地缓存移除 |
| 409 | `STATE_MACHINE_VIOLATION` | 任务状态不允许该流转（`details.currentStatus`） | **刷新任务详情**，提示"任务状态已变化" |
| 409 | `EDIT_WINDOW_EXPIRED` | 超过 15 分钟编辑窗口 | 提示改为"撤回后重发" |
| 409 | `DELETE_WINDOW_EXPIRED` | 超 2 分钟且无权撤回他人消息 | 提示无权限 |
| 409 | `GROUP_ARCHIVED` | 向归档群写 | 置灰输入框，提示群已归档 |
| 413 | `PAYLOAD_TOO_LARGE` | 超单文件或请求体上限 | 提示大小超限 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | 类型不在白名单，或**魔数与声明不符** | 提示不支持的文件类型 |
| 422 | `HASH_MISMATCH` | 上传完成时 sha256 不符 | 提示重新上传 |
| 429 | `RATE_LIMITED` | 触发限流（响应带 `Retry-After`） | 倒计时后自动重试 |
| 500 | `INTERNAL` | 未预期错误 | 提示稍后重试 + 上报 `requestId` |
| 503 | `NOT_READY` | `/readyz` 未就绪（如 DB 断连） | 显示维护横幅，配合自动重连 |

**一个刻意的例外**：`message:send` 命中幂等（`clientMsgId` 已存在）时返回 **`200` + `deduplicated: true` + 原消息**，而不是 `409`。幂等命中是**正常路径**（弱网重试必然发生），不是错误。如果返回错误码，前端的重试逻辑会把它当成失败并继续重试，形成循环。

### 8.2 限流

单进程内用令牌桶（key 为"路由 + 维度"），**限流检查必须在任何数据库操作之前**，否则限流本身不省资源。

| 接口 | 维度 | 限额 | 理由 |
|---|---|---|---|
| `POST /auth/login` | IP | 5 / 分钟 | 防撞库 |
| `POST /auth/login` | 用户名 | 10 / 小时 | 防换 IP 打同一账号（**两个维度都要，缺一个都能被绕过**） |
| `POST /auth/register` | IP | 3 / 小时 | 邀请码也会被爆破 |
| `POST /auth/refresh` | 会话 family | 30 / 分钟 | 防刷新风暴（客户端 bug 导致的死循环刷新） |
| 发消息（WS 与 HTTP 共用计数） | 用户 × 群 | 30 / 分钟 | 防刷屏 |
| 发消息 | 用户（全局） | 200 / 分钟 | 防跨群刷 |
| 文件上传 | 用户 | 20 / 小时 | 防磁盘被瞬间打满 |
| 搜索 | 用户 | 60 / 分钟 | 搜索是最重的读操作 |
| 创建任务 / 评论 | 用户 | 120 / 小时 | |
| `/hooks/*` | 来源（HMAC key） | 120 / 分钟 | 防告警风暴打垮后端（**告警风暴本身就是故障场景，此时后端必须活着**） |
| 其他写接口 | 用户 | 600 / 分钟 | 兜底 |

**告警接口的限流要特别说明**：磁盘满或服务反复重启时，Uptime Kuma 与巡检脚本可能在短时间内大量报同一件事。**此时后端必须能承受，否则"告警把系统压垮"会成为二次故障**。所以 `/hooks/alert` 除了限流，还有幂等（`idempotencyKey`）与聚合（同 `(source, title)` 在 5 分钟内合并为一条计数消息）。

### 8.3 文件上传安全

| 项 | 规则 | 防止 |
|---|---|---|
| 单文件上限 | **50MB** | 磁盘与内存被打爆 |
| 单用户配额 | **2GB**（`sum(byte_size) where uploader_id = X and status <> 'cleaned'`） | 一个用户占满磁盘 |
| MIME 白名单 | `image/jpeg`、`image/png`、`image/gif`、`image/webp`、`application/pdf`、`text/plain`、`text/csv`、`application/zip`、`application/vnd.openxmlformats-officedocument.*`（docx/xlsx/pptx）、`application/msword`、`application/vnd.ms-excel`、`application/vnd.ms-powerpoint` | 上传可执行文件 |
| **明确拒绝 SVG** | `image/svg+xml` 不在白名单 | **SVG 可内嵌 `<script>`，是存储型 XSS 的经典载体**。即使只在下载时才渲染，浏览器直接打开 SVG 也会执行脚本 |
| **魔数校验** | 读文件头比对声明的类型。例如 JPEG 必须 `FF D8 FF`、PNG 必须 `89 50 4E 47`、PDF 必须 `%PDF-`、ZIP 系（docx/xlsx/pptx）必须 `50 4B 03 04`。不符则 `415 UNSUPPORTED_MEDIA_TYPE` | **改后缀名绕过白名单**——这是最容易漏的一步。不信 `Content-Type`，也不信文件名 |
| **object_key 服务端生成** | `{yyyy}/{mm}/{uuid}.{ext}`，`ext` 从魔数判定结果取，**绝不使用用户提供的文件名** | 路径穿越（`../../etc/passwd`）、覆盖已有文件、超长/特殊字符文件名 |
| 上传目录位置 | 不在任何 web root 下，只通过签名 URL 提供 | 直接 URL 猜解访问 |
| 下载方式 | 302 重定向到**签名 URL**（HMAC，有效期 10 分钟），由 Caddy 直接发文件 | Node 承载文件流会阻塞事件循环、放大内存占用 |
| 下载响应头 | 非图片加 `Content-Disposition: attachment`；全部加 `X-Content-Type-Options: nosniff` 与 `Content-Security-Policy: default-src 'none'; sandbox` | 浏览器把附件当 HTML 渲染导致 XSS |
| 图片重编码 | `sharp` 读取后重新编码输出（缩略图与原图都重编码），**不直接透传上传的原始字节** | 畸形图片数据触发的解析器漏洞；同时顺带**剥离 EXIF**（含 GPS 定位） |
| 图片压缩参数 | 最长边 1600px、quality 78；缩略图最长边 320px、quality 70 | 3-5Mbps 出口带宽下原图直出会拖死所有人（见 6.10） |
| 缩略图失败 | 生成失败即拒绝上传（`415`） | 说明"图片"其实不是有效图片 |
| 上传临时文件 | `pending` 状态的文件若 24 小时内未 `complete`，由清理任务删除 | 用上传接口堆垃圾文件占磁盘 |

**签名 URL 的格式**（与 `03-AI运维手册.md` 里 Caddy 的配置对应）：

```
/_files/{object_key}?exp={unix_ts}&sig={hmac_sha256(object_key + exp, SECRET)}
```

签名校验由 **Caddy 侧不需要做**——由后端在签发时保证，Caddy 只负责检查 `exp` 与发文件。因此 **`exp` 必须由 Caddy 校验**（`Caddyfile` 里用 `@expired` matcher），否则签名链接永久有效，等于没有鉴权。这一点在运维册里配置时必须落实。

### 9.2 对账与自检项（进程内定时任务）

这些检查的作用是**发现"数据层面已经不一致但功能看起来正常"的情况**。这类问题如果不主动检查，会一直静默累积，直到某天统计报表明显不对才被发现。

| 检查 | 频率 | 不一致时的含义 |
|---|---|---|
| `groups.last_seq >= max(messages.seq)` | 每小时 | 出现 `last_seq` 小于实际最大 `seq`，说明有人绕过分配器直接写 `seq` |
| 打回次数对账：`task_status_history` 的 `submitted→in_progress` 计数 vs `task_acceptances` 中 `result='rejected'` 的轮次数 | 每天 | 状态机与历史表写入不一致（事务边界写错） |
| `outbox` 积压（`processed_at IS NULL` 计数） | 每 5 分钟 | Meilisearch 挂了或 worker 停止 |
| presence 泄漏：`io.engine.clientsCount` vs presence 集合总数 | 每 30 秒 | 死连接未清理（4.6） |
| `files.ref_count` 与实际引用数抽样比对 | 每天 | 触发器失效或有人手工改数据 |
| `pending` 状态的 attachments 悬挂（外键应保证不会发生，作为兜底） | 每天 | 数据被外部工具直接修改 |

结果写入日志与 `/internal/metrics`，**异常项由巡检脚本判定后推送到 `#运维告警` 群**（见 `03-AI运维手册.md`）。

## 附录 A：本册对运行环境的要求

本册不重复部署步骤（见 `04-服务器租赁与部署说明.md`），但应用**要求**以下配置存在，缺失会导致启动失败或功能静默异常。`config/env.ts` 在启动时校验，**缺失即退出**（不留到运行时才发现）。

| 变量 | 必需 | 用途 | 缺失后果 |
|---|---|---|---|
| `NODE_ENV` | ✓ | 决定 Zod 出参校验的严格程度 | 生产环境会退化为宽松模式 |
| `PORT` | ✓ | HTTP 监听端口（默认 3000） | — |
| `DATABASE_URL` | ✓ | PG 连接串 | 无法启动 |
| `JWT_SECRET` | ✓ | access token 签发 + 签名 URL 的 HMAC 密钥派生 | 无法启动 |
| `UPLOAD_DIR` | ✓ | 附件存储根目录（容器内路径） | 无法启动 |
| `PUBLIC_ORIGIN` | ✓ | 生成签名 URL 与告警回调地址 | 签名 URL 错误 |
| `MEILI_URL` / `MEILI_MASTER_KEY` | ✓ | 搜索服务 | 启动失败（**刻意要求**：配置错误应当在启动时暴露，而不是等用户搜索时才发现） |
| `ALERT_HMAC_SECRET` | ✓ | `/hooks/*` 的签名校验 | 告警接口不可用 |
| `LOG_LEVEL` | | 默认 `info` | — |
| `SYSTEM_GROUP_ID` | | `#运维告警` 群的 ID | 启动后由 CLI 脚本写入；缺失时告警接口返回 `503` |
| `OPS_APPROVER_GROUP_ID` | | 审批权限来源群 | 同上 |
| `CONTRACT_VERSION` | | 通常由构建时注入，无需手工配置 | 前端版本守卫退化为禁用 |

**`SYSTEM_GROUP_ID` 的初始化顺序**：首次部署后必须执行 `node dist/cli/create-admin.js`（创建首个用户 + 系统群 + 邀请码），再把输出的群 ID 写入环境变量并重启 API。这个顺序不在应用内自动化——**自动创建系统群会在"环境变量为空"时反复失败，而失败原因在日志里看起来像数据库问题，很难定位**。让运维显式做这一步，比埋一个自动化的坑好。
